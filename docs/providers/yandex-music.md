# Яндекс Музыка API

Статус: исходники актуальной community-библиотеки и её документация просмотрены 28.10.2026. API неофициальный и обратным проектированием восстановлен сообществом; официального открытого Web API для этой интеграции не найдено.

## Библиотека и авторизация

Основной кандидат — [MarshalX/yandex-music-api](https://github.com/MarshalX/yandex-music-api), LGPL-3.0. В проверенном срезе GitHub: последний опубликованный релиз `v3.2.2`, исходный commit `9ca132e` (2026-10-11), репозиторий обновлялся 2026-10-26. Поддерживает sync/async клиент; OpenAPI справочник, генерируемый из реализации библиотеки, описывает около 150 операций и 220 схем. Сверяйте детали с конкретной версией перед реализацией.

### Страничный мост к очереди: `Night-Soft/YmExternalAPI`

В актуальном на 27.10.2026 публичном checkout [`Night-Soft/YmExternalAPI`](https://github.com/Night-Soft/YmExternalAPI/tree/a61c8011affeda77c855dcb1f96a9a4b3e000783) (версия 1.3.2, HEAD `a61c8011affeda77c855dcb1f96a9a4b3e000783`, push 2026-08-31) найден вариант взаимодействия с уже открытой страницей без чтения browser cookies или OAuth bearer. Расширение объявляет content script в `world: MAIN` на `document_start`, перехватывает webpack runtime и достаёт внутренние controller/store; публичных `host_permissions`/`permissions` в manifest нет. Это всё равно доступ к внутренним нестабильным объектам сайта, а не официальный стабильный API.

| Метод страницы | Что возвращает / делает | Ограничение для экспорта |
|---|---|---|
| `externalAPI.getTracksList()` | `Tracks.converted` для `Controller.state.queueState.entityList.value`; у элемента `title`, `version`, `cover`, `duration`, `liked`, `disliked`, `link`, первый album, artists | Текущий список/очередь плеера; нет track ID, total, cursor, revision или доказанного обхода всей библиотеки лайков |
| `externalAPI.getSourceInfo()` | Метаданные текущего источника воспроизведения | Само по себе не перечисляет пользовательскую коллекцию |
| `externalAPI.populate(fromIndex, after?, before?)` | Подгружает unloaded entities текущей очереди; defaults: 25 после и 15 перед индексом; возвращает Promise | Это hydrate по индексам очереди, а не page API коллекции; границы и наличие полного liked playlist зависят от source context. `ordered` указан в README как не реализованный |
| `externalAPI.toggleLike()` / `toggleDislike()` | Меняет лайк/дизлайк текущего трека через внутренний likeStore | Изменяющие операции; не вызывать в read-only connector |

Source scan pinned HEAD не нашёл использования `chrome.cookies`, `document.cookie`, Web Storage, Authorization bearer или извлечения OAuth token. Поле `liked` формируется через внутренний `likeStore`, но наличие этого флага у элементов текущей очереди не означает, что `getTracksList()` возвращает все лайки. В manifest нет `LICENSE`, а GitHub license metadata пустая: код нельзя включать в наш продукт до выяснения лицензии. Browser-проверка публичного GitHub README подтвердила заявленное предупреждение о неофициальности; clone/source review в терминале подтверждает структуру выше. Расширение не устанавливалось и на пользовательском аккаунте не запускалось.

Практическая ценность — минимальный прототип user-in-page connector: на вкладке пользователя считывать нормализованные поля очереди и отправлять приложению только данные треков. Перед применением к лайкам нужно на фиктивном/тестовом контексте определить, как пользователь может явно открыть полный liked-list source, измерить доступную длину, проверить пропуски и выяснить, можно ли надёжно получить ID. Не добавлять автоматический `play`, `toggleLike` или другие действия над аккаунтом.

Полный индекс всех операций pinned OpenAPI snapshot вынесен в [Yandex Music community API inventory](yandex-openapi-inventory.md): он содержит 150 методов по 22 категориям, включая likes/dislikes, playlist, library/profile, search, track/album/artist, radio, history и account-settings routes. Спецификация задаёт server `https://api.music.yandex.net` и глобальный `Authorization: OAuth <token>`; device-code/token endpoints явно без этой схемы.

Host difference: library/OpenAPI snapshot использует `api.music.yandex.net`, а ранее наблюдавшийся Chrome и authenticated terminal traffic для account/likes/details шёл на `api.music.yandex.ru` и отвечал `200`. No-auth `/search` отдельно ответил `200 application/json` на обоих доменах 27.10.2026. Это не доказывает, что все routes взаимозаменяемы; сохранять фактический host как часть проверенного request profile и перепроверять перед реализацией.

### Независимый Go-клиент `DECE2183/yamusic-tui`

Закреплён публичный [`DECE2183/yamusic-tui`](https://github.com/DECE2183/yamusic-tui/tree/4d543ae9029618dd510f9b21599988eaab45845a) на HEAD `4d543ae9029618dd510f9b21599988eaab45845a` (GPL-3.0; commit 2026-10-26, release `v0.8.0` от 2026-09-11). README браузером подтвердил, что это активный неофициальный TUI; в README прямо сказано, что приложение требует пользовательский token, а интерфейс предлагает его вставить. OAuth authorization в обычном сценарии приложения нет.

`api/api.go` даёт ещё один source cross-check маршрутов и HTTP-форм:

| Операция | Метод и путь | Форма / ограничения в checked source |
|---|---|---|
| Проверить статус, получить UID | `GET /account/status` | `Authorization: OAuth <token>` |
| Получить лайки треков | `GET /users/{uid}/likes/tracks` | `LikesDesc.Library.Tracks`; без cursor, revision или client-side pagination |

| Поставить/снять like | `POST /users/{uid}/likes/tracks/add-multiple`; `POST /users/{uid}/likes/tracks/remove` | form-urlencoded `track-ids`; мутации не выполнялись |
| Изменить playlist | `POST /users/{uid}/playlists/create`, `/name`, `/delete`, `/change-relative` | form-urlencoded title/visibility, name, revision/diff; мутации не выполнялись |

Token хранится plaintext в `~/.config/yamusic-tui/config.yaml`: код запрашивает mode `0755` для directory и файла, что допускает group/world read, если права не урежет системный umask. В `api/constants.go` также есть неиспользуемый обычным UI deprecated password-grant helper и встроенные shared OAuth client credentials; значения не переносим. Клиент GPL-3.0, не Apple importer; его код полезен как маршрутный cross-check, но не как готовый auth connector или безопасное хранилище.

Свежая проверка без авторизации: публичная GitHub-страница HEAD открылась в Chrome и показала release/README; затем чистый Python `urllib` GET дал `200 application/json` для `/account/status` и `403 application/json` для synthetic `/users/1/likes/tracks?if-modified-since-revision=0`. Тела ответов не читались и не сохранялись. `go version` не запустился (`go` отсутствует), поэтому Go tests/build не проверялись. Ни браузерные cookies/tokens, ни пользовательские данные не использовались.

### Public playlist routes из `YandexMusicExport`

Статически просмотрен [YMusicExport/YandexMusicExport](https://github.com/YMusicExport/YandexMusicExport/tree/c80db0a54db7f1e67646695f1247292ab57e100b), HEAD `c80db0a54db7` от 16.05.2026, без declared license. В коде без auth headers используются два GET:

- `https://music.yandex.ru/handlers/playlist.jsx?owner={owner}&kinds={kind}` — legacy route, читает `playlist.title` и `playlist.tracks`.
- `https://api.music.yandex.ru/playlist/{playlist_uuid}` — route для новых ссылок, читает `result.title` и `result.tracks[].track`.

Это только статическая проверка кода, endpoints этим проектом здесь не запрашивались. README ограничивает сценарий публичными плейлистами; private «Мне нравится» не поддерживается. Скрипт теряет provider IDs в текстовом output. Community OpenAPI отдельно индексирует `/playlist/{playlist_uuid}`; live no-auth доступность и pagination/лимиты требуют отдельной проверки, поэтому не считать route доказанным источником полного лайк-списка.

В библиотеке есть OAuth Device Flow. `POST https://oauth.yandex.ru/device/code` передаёт form-urlencoded `client_id`, `device_id` и `device_name`; по умолчанию библиотека генерирует `device_id` из 10 символов, а имя задаёт `YandexMusicAPI`. Ответная модель описана полями `device_code`, `user_code`, `verification_url`, `expires_in` и `interval`. Пользователь открывает verification URL и подтверждает код на домене Яндекса.

Затем библиотека делает `POST https://oauth.yandex.ru/token` с form-urlencoded полями `grant_type=device_code`, `code`, `client_id` и `client_secret`. В проверенном commit вшиты credentials публичного Android-клиента Яндекс Музыки; это не credentials, выданные нашему приложению, и встроенный `client_secret` нельзя считать секретом проекта. Значения самих credentials в документацию не копируем. Polling следует выполнять с интервалом `interval` и до срока `expires_in` из device-code ответа: `authorization_pending` возвращается как `None`, а `expired_token`, `access_denied`, `invalid_client` и другие OAuth ошибки приводят к `DeviceAuthError`. Блокирующий helper также поддерживает timeout и отмену. При успехе он записывает access token в клиент и добавляет `Authorization: OAuth <token>`.

Ответ token-модели содержит `access_token`, `refresh_token`, `expires_in` и `token_type`, но эта библиотека не сохраняет токены и не обновляет access token автоматически. Хранение и срок жизни — ответственность приложения; поведение refresh token этим клиентом не реализовано.

### Browser extension: `MarshalX/yandex-music-token`

В репозитории [MarshalX/yandex-music-token](https://github.com/MarshalX/yandex-music-token), HEAD `4d90e6b` (2026-07-23, MIT), есть Chrome/Firefox extension, который действительно может получить токен через браузер, но он **не извлекает cookie или уже работающий токен из страницы Яндекс Музыки**. `background.js` открывает `https://oauth.yandex.ru/authorize?response_type=token&client_id=<app-id>`, слушает URL OAuth-вкладки и читает `access_token` из fragment после редиректа на `music.yandex.ru`. Токен сохраняется в `chrome.storage.local`; в той же callback-ветке расширение затем открывает Telegram bot URL, передавая токен как `start` параметр. Popup также может скопировать сохранённый токен или очистить extension storage.

Слепо использовать расширение для нашего импортёра нельзя: это implicit OAuth с токеном в URL fragment, hardcoded client ID общей OAuth app и автоматической передачей токена в Telegram bot URL. Публичный endpoint `https://oauth.yandex.com/client/23cabbbdc6cd418abb4b39c32c41195d/info` ответил `200 application/json`; app `Яндекс.Музыка` разрешает 19 scope, включая `music:read`/`music:write`, `payments:all`, `yadisk:disk`, профильные права, mobile services и smart-home/device rights. Это совпадает по сути с ранее увиденным чрезмерно широким consent screen. Права могут меняться владельцем OAuth app, поэтому значение получено 27.10.2026 и требует повторной проверки.

Сам технический приём — открыть провайдерский OAuth в отдельной вкладке и перехватить callback fragment **локально** — можно адаптировать, если приложение имеет подходящий consent scope и не пересылает токен наружу. Но повторение flow этого расширения выдаёт именно перечисленные разрешения и не решает минимизацию доступа. Для текущего проекта безопаснее исследовать прямое использование локальной cookie-сессии или найти отдельный app/client с только музыкальными правами. Extension просмотрен статически, не установлен и не запускался; токен не запрашивался.

В актуальном checkout на том же pinned HEAD проверен и `web-app/`: это статический frontend без собственного backend, с Device Code Flow и кнопкой показа/копирования результата. Device route делает `POST /device/code`, затем опрашивает `POST /token`; токен находится в состоянии страницы и показывается пользователю. При этом опубликованный frontend содержит shared `client_id` и `client_secret` для обеих операций: секрет нельзя считать конфиденциальным в публичном JavaScript, а разрешение привязано к чужому OAuth app. Там же есть скрытая по умолчанию password-grant форма: она отправляет введённые логин/пароль напрямую на OAuth endpoint Яндекса, с обработкой CAPTCHA. Это не следует использовать в нашем UX и в этой проверке не запускалось. В extension OAuth callback хранит token в `chrome.storage.local`, затем открывает Telegram URL с токеном в query parameter. Вывод: хороший reference для интерфейса Device Flow и локального получения результата, но не готовый безопасный connector; для проекта лучше передавать локальному UI только результат экспорта, не постоянный bearer.

Актуальный публичный source: [`web-app/src/api.ts` на pinned HEAD](https://github.com/MarshalX/yandex-music-token/blob/4d90e6b25cccf99d53893b0597272ddb5c3651bf/web-app/src/api.ts), [`web-app/src/main.ts`](https://github.com/MarshalX/yandex-music-token/blob/4d90e6b25cccf99d53893b0597272ddb5c3651bf/web-app/src/main.ts), [`extension background.js`](https://github.com/MarshalX/yandex-music-token/blob/4d90e6b25cccf99d53893b0597272ddb5c3651bf/browser-extension/src/background.js).

### Перехват токена из уже открытой страницы: `vladimir120307-droid/yandex-music-downloader`

Отдельный и более близкий к вопросу пользователя пример — [Music Downloader](https://github.com/vladimir120307-droid/yandex-music-downloader), pinned HEAD `1cbf2fc` (2026-09-10; по README Chromium extension для Яндекс Музыки, Bandcamp и SoundCloud). В `inject/yam-fetch-hook.js` расширение запускает скрипт в `MAIN` world на `document_start`, оборачивает `window.fetch` и `XMLHttpRequest` и читает `Authorization: OAuth/Bearer ...` из исходящих запросов страницы только к `api.music.yandex.net`. Через `window.postMessage` значение передаётся content script; `content.js` сохраняет его в `chrome.storage.local` как `yamToken`, после чего `services/yandex.js` использует его в OAuth-заголовке для прямых API-запросов. Здесь токен действительно извлекается из текущей авторизованной сессии сайта, а не получается новым OAuth consent flow.

Это технически переносимый приём для принадлежащего пользователю браузерного коннектора. В просмотренной реализации токен хранится постоянно в extension storage и используется downloader-ом; для Music Importer лучше не копировать модель хранения. Расширение может выполнять только нужный read-only запрос в контексте текущего сайта и передавать локальному приложению нормализованные треки/страницы без bearer token. Скрипт и manifest просмотрены статически; расширение не устанавливалось и не запускалось, актуальность HEAD следует перепроверить перед повторным использованием.

### Найденный QR-вход: `jrfrigat/YandexMusic` for .NET

Свежий GitHub поиск обнаружил MIT client [jrfrigat/YandexMusic](https://github.com/jrfrigat/YandexMusic), HEAD `8c929094386137669766632f9cc2c97d3b05f670` (17.10.2026). По README это async .NET API с каталогом, library likes и несколькими способами входа: OAuth token, device code, Passport QR, session cookies и login/password. Он покрывает те же likes route families, что уже известный Python client: `GET /users/{uid}/likes/tracks?if-modified-since-revision=...`, `POST .../add-multiple`, `POST .../remove`; авторизация API передаётся как `Authorization: OAuth <token>`. Конкретная реализация есть в pinned [`LibraryClient.cs`](https://github.com/jrfrigat/YandexMusic/blob/8c929094386137669766632f9cc2c97d3b05f670/src/YandexMusic/Endpoints/LibraryClient.cs).

QR implementation в [`PassportAuthenticator.cs`](https://github.com/jrfrigat/YandexMusic/blob/8c929094386137669766632f9cc2c97d3b05f670/src/YandexMusic/Authentication/PassportAuthenticator.cs) создаёт Passport session, показывает пользователю magic-link/QR для подтверждения, опрашивает статус, а после подтверждения обменивает session cookies на Music access token через OAuth implicit redirect. Пользователю не нужно вводить пароль в клиент. Однако сам исходник прямо называет Passport QR/cookie flows undocumented и best-effort; используется встроенный shared Music client ID. Отдельный device-code flow требует app credentials по умолчанию зашитые в библиотеку; практическая проверка другого Android client уже показала избыточные scopes. Поэтому QR — интересный входной UX для прототипа, но его consent/scopes, server behavior, expiry и refresh нужно проверить до выбора.

Реализация также предоставляет отдельный login/password flow, который отправляет пароль на Passport endpoint; для импортёра не использовать его. [`AuthSession.Export()`](https://github.com/jrfrigat/YandexMusic/blob/8c929094386137669766632f9cc2c97d3b05f670/src/YandexMusic/Authentication/AuthSession.cs) включает access token и все session cookies в snapshot, поэтому сериализуемую сессию нельзя хранить открытым текстом. Этот кандидат проверен статически по исходникам, не собирался и не запускался; это дополнительная реализация и UX-reference, а не подтверждение работы live QR.

### Практическая проверка Device Flow, 27.10.2026

Из pinned source были использованы публичные credentials Android-приложения Яндекс Музыки для read-only auth probe. `POST /device/code` вернул device/user code, verification URL, срок действия и интервал polling. Verification page открылась в уже авторизованном Chrome; после ввода user code Яндекс показал экран согласия для приложения «Яндекс.Музыка». Запрошенные scopes оказались значительно шире чтения музыкальной библиотеки: доступ к личным данным в сервисах Яндекса, профиль/дата рождения/email/имя, чтение и **изменение** плейлистов, чат с поддержкой, платежи/история платежей, DataSync, Яндекс.Диск, умный дом и другие разрешения. Такой grant превышает необходимый объём для экспорта лайков, поэтому согласие отменили и терминальный polling завершили до получения токена. Ни OAuth access/refresh token, ни account/track data из этого Device Flow не получали и не сохраняли; коллекция не менялась. Это практическое подтверждение работы code request и одновременно подтверждение, что встроенный Android OAuth client не годится для least-privilege входа проекта без явного разбора scopes. Некоторые аккаунты/регионы/режимы могут не пройти этот неофициальный flow.

Вход через логин/пароль не нужен для рекомендуемого прототипа. Токен — секрет; не коммитить и не печатать в лог.

## Операции с лайками

В этой версии библиотека реализует следующие HTTP-шаблоны (это reverse-engineered контракт библиотеки, не официальная спецификация Яндекса):

- `GET /users/{user_id}/likes/tracks` — список лайкнутых треков (`users_likes_tracks()`); если `user_id` не передан, библиотека использует UID текущего аккаунта. Метод передаёт query parameter `if-modified-since-revision` (по умолчанию `0`). Код и community OpenAPI не описывают `offset`, `limit` или cursor для этой операции.
- Ответ описан как `TracksList { uid, revision, tracks[] }`, где элементы — `TrackShort`; у модели нет page/cursor полей. Read-only terminal replay на текущем аккаунте сравнил conditional запросы: при `if-modified-since-revision`, равном текущей `revision`, сервер вернул HTTP 200 со строковым `result` и без `library`; при значении на единицу меньше вернул HTTP 200 с объектом `library` и массивом `tracks`. Это указывает, что текущая revision подавляет повторную выдачу списка, а устаревшая revision возвращает библиотеку. Точный контракт строки и прочие случаи остаются неописанными в официальной спецификации; community-клиент помечает семантику TODO и преобразует non-dict result в `None`. Для первого полного чтения используйте `0` (или не передавайте параметр), а conditional sync стройте только после проверки конкретной формы ответа.
- `POST /users/{user_id}/likes/tracks/add-multiple` и `/remove` — изменить лайк (`users_likes_tracks_add`/`_remove`). Community OpenAPI указывает `application/x-www-form-urlencoded` и поле `track-ids` (описанное как string), не JSON. Библиотека принимает ID как list/string/int и передаёт словарь через `requests` `data=`; точный wire format списка и то, какие варианты принимает сервер, требуют отдельной контролируемой проверки. Максимальный размер пачки также не зафиксирован.
- `POST /tracks` — получить карточки по набору ID; community OpenAPI также помечает тело как `application/x-www-form-urlencoded`, поля `track-ids` и `with-positions`. В ранее проверенном единичном terminal-запросе form body `track-ids=<id>` вернул карточку; JSON-array формат дал `400`.

Реализация `_like_action` считает операцию успешной по наличию `revision` в ответе для треков. В изученном исходнике не обнаружено зафиксированного стабильного максимального размера пачки: его нельзя предполагать, нужно выяснять тестом и учитывать ответы сервиса.

Но Apple web-session tokens надо вручную передать локальному процессу, путь не поддержан Apple, HTTP `202`/`state.json` не подтверждаются чтением результата, а live mutation не выполнялась. ### Прямой pipeline: `ComputerPers/YandexMusic_to_AppleMusic`

В [ComputerPers/YandexMusic_to_AppleMusic](https://github.com/ComputerPers/YandexMusic_to_AppleMusic), проверенный HEAD `41fdd0e` от 07.04.2026 (GitHub не показывает объявленную лицензию), экспорт вызывает `users_likes_tracks()`, затем запрашивает подробности через `POST /tracks` батчами по 100. JSON сохраняет Yandex ID, title, artists, album, duration; CSV опускает внутренний список артистов. ISRC и исходный порядок/позиции лайков не сохраняются. Сам лимит списка лайков не проверен; в используемой библиотеке нет явной cursor-пагинации.

Его локальный Apple destination path (`add_to_apple_music.py`) принимает результаты matcher, открывает `apple_url` как `music://` в Music.app, затем AppleScript запускает запись, дублирует `current track` в Library и ищет запись по title+artist (fallback только по title), после чего дублирует её в плейлист `Yandex Favorites`. Это не выставляет Favorite; дополнительный gist выше показывает отдельный последующий setter. Скрипт ждёт около 10 секунд на трек и печатает title/artist; восстановление возможно через `--from`, но защита от дублей по уже добавленным записям не обнаружена. Static only, не запускался.

Сопоставление идёт через публичный `GET https://itunes.apple.com/search` (`term`, `media=music`, `entity=song`, `limit`, `country`), ищет в `ru` и `us`, запрашивает до 25 результатов и использует нормализацию плюс substring-проверку title/artist. ISRC-first стратегии нет. Результаты можно проверить по JSON/отчёту несовпадений и продолжить после прерывания; matcher делает несколько поисков на трек с задержкой 3,5 секунды.

Apple API-вариант проверяет `GET /v1/me/library/songs?limit=1`, добавляет catalog song IDs через `POST /v1/me/library?ids[songs]=...` порциями по 25 и может создать playlist через `POST /v1/me/library/playlists`, затем дополнять `POST /v1/me/library/playlists/{id}/tracks`. Принятие в библиотеку считается успешным при HTTP 202. Ни этот writer, ни AppleScript-вариант не вызывают Favorite Songs route `/v1/me/favorites`: они добавляют в Library и отдельный playlist, поэтому сохранённые исходные лайки не становятся Apple Favorites.

Локальный writer открывает `music://` track URL, запускает воспроизведение и дублирует current track в Library и playlist. Поиск для playlist сначала использует название+артиста, затем fallback только по названию; это может выбрать неверную одноимённую запись. Режима установить `track.favorited` в просмотренном коде нет.

Токенный helper не является надёжным Chrome extractor на macOS: он копирует целиком SQLite Cookies database во временный файл, ищет `media-user-token`, а для encrypted value с префиксом `v10` сразу останавливается с инструкцией скопировать cookie вручную; temporary copy удаляется в `finally`. В коде нет вызова Keychain/decryption. Для иных префиксов он пробует UTF-8 decode, что не доказывает успешную расшифровку. Developer token скрейпится из JavaScript bundle `beta.music.apple.com` и частично печатается; при `--save` оба токена записываются открытым текстом без задания ограниченного file mode (файлы лишь перечислены в `.gitignore`). `--dry-run` в API-варианте всё ещё загружает токены и выполняет auth-check до выхода. Это полезный reference на общий экспорт→match→review pipeline, но не готовый import в Favorite Songs и не образец session/token handling.

Дополнительная реализация в [oklookat/synchro](https://github.com/oklookat/synchro), HEAD `ac441f4` от 2024-07-07 (GPL-3.0), использует Go-клиент `goym`: OAuth Device Flow с credentials публичного Android-клиента, чтение `LikedTracks`, загрузку metadata пачками по 30 и методы `LikeTracks`/`UnlikeTracks`. В просмотренной версии `LikedTracks` отбрасывает UGC записи; это означает, что такой экспорт не гарантированно сохраняет весь список лайков. Код старый и хранит auth в SQLite без шифрования, поэтому годится только как reference операций, не как готовое приложение.

### Chrome UI-triggered маршрут лайков (28.10.2026)

В существующей Chrome-сессии выбран видимый пункт «Мне нравится». UI-навигация на `music.yandex.ru/playlists/:id` получила `200`; в том же переходе браузер инициировал `GET https://api.music.yandex.ru/playlist/:id?resumeStream=…&richTracks=…` и preflight `OPTIONS` на этот путь. ID приватного liked-list нормализован; значения query, заголовки, response body и трековые данные не читались/не сохранялись. Для API GET статус в этой capture не зафиксирован, поэтому запрос доказывает только маршрут и параметры, не успешный ответ или полноту экспортируемого списка. No-cookie terminal проверки других приватных routes остаются описаны выше.

## Оценка

Подходит как источник лайков для локального прототипа и для дальнейшей поддержки. Риски: нестабильный контракт, зависимость от OAuth credentials стороннего клиента, разная доступность по аккаунтам, и лицензия LGPL-3.0 при возможном включении библиотеки в проект. Для MVP лучше начать read-only экспорт, сохранить полный каталог, затем отдельно проверить изменение лайка на собственном аккаунте.

## Официальный перенос и архив аккаунта

Официальная [справка Яндекс Музыки](https://www.yandex.ru/support/music/ru/collection/sync-and-transfer) описывает импорт коллекций **в Яндекс Музыку**: пользователь входит в Яндекс, выбирает сторонний сервис, авторизуется в нём и запускает перенос; результат появляется в Коллекции и плейлистах. Это подтверждает, что у Яндекса есть отдельная интеграция-агрегатор, но она не экспортирует Яндекс → Apple и не даёт нам публичный API для чтения лайков.

Та же инструкция описывает передачу между Яндекс-аккаунтами через публикацию playlist «Мне нравится» и повторное добавление его в другом аккаунте. Это создаёт/подписывает обычный playlist, не переносит Favorite Songs в Apple и требует изменить приватность исходного списка; не использовать как основной importer.

В [Yandex personal-data guide](https://yandex.com/support/m-yandex/en/privacy/clear-data) описан запрос password-protected account archive через Your Data. Документация не указывает, что архив содержит полный экспорт музыкальных likes или пригодный JSON/CSV track list. Поэтому этот архив — лишь исследуемая возможность, а не подтверждённая замена API. Если пользователь вручную получит его, сначала проверить список файлов и поля локально, не сохранять архив в репозитории и не загружать на сервер.

## Chrome extension collector: krav-ets/yandex-music-exporter-extension

В pinned HEAD bd48a4fbb74902baad4788a0960b7a0863ca8131 найден не OAuth/token extension, а локальный API-response collector.

- Manifest MV3 запускает скрипт в MAIN world на document_start для music.yandex.ru/.com; host permissions ограничены этими доменами. Запрошены activeTab, downloads, storage, tabs, unlimitedStorage; cookies permission отсутствует.
- В режиме playlist collector перехватывает вызов window.fetch текущей страницы, добавляет richTracks=true к любому GET URL с path /playlist, читает только response.clone().json() и отдаёт оригинальный response плееру. В режиме accumulation пассивно сохраняет JSON responses к Yandex URLs, похожим на tracks/playlist/likes/library, когда пользователь листает страницу.
- Isolated content script принимает capture через same-origin postMessage, а service worker сохраняет сырые response bodies в chrome.storage.local; CSV содержит только title/artist/album, raw JSON export включает полные response payloads. Данные очищаются при закрытии панели/перезагрузке tab, а не отправляются на внешний server. Token/cookie values отдельно не читаются и не экспортируются.
- Для liked list потенциально можно открыть music.yandex.ru/playlists/lk.<uuid> и проверить, отдаст ли web player GET /playlist/... с полной tracks[]; это предположение из URL/filter logic, README заявляет только playlists. trackCount отображается рядом с извлечённым количеством, но source не сравнивает значения и не сверяет revision/cursor. Полнота «Мне нравится» не доказана.
- GitHub metadata/checkout не содержат license declaration/LICENSE. Публичный README в Chrome и pinned source в terminal просмотрены; расширение не установлено и не запускалось, поэтому live behavior private liked list не проверен.

Это перспективный локальный page bridge: на вкладке пользователя считывает response API и отдаёт его локальному UI без копирования session secret. До прототипирования нужно проверить read-only liked page, совпадение объявленного total с items и полноту response; не вызывать операции, меняющие лайки.
