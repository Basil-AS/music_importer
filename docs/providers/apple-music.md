# Apple Music API / MusicKit

Статус: официальная документация и авторизованный Apple Music Web проверены 27.10.2026. В качестве назначения важно переносить понравившиеся композиции именно в Apple Favorite Songs, если пользователь под «лайками» имеет это в виду; не просто складывать их в отдельный плейлист.

Полный индекс официальной Apple Music REST API построен из текущего Apple Developer DocC каталога: [138 операций, 119 уникальных method/path пар](apple-openapi-inventory.md). Ниже оставлены детали, относящиеся к миграции и практической проверке.

## Авторизация

Apple API различает developer token, подписанный разработчиком JWT, и Music User Token, который разрешает пользовательские операции. Вручную созданный developer token — JWT с ES256 и `kid`, Team ID в `iss` и максимальным сроком `exp` до шести месяцев; Apple указывает, что он предназначен для участника Apple Developer Program. Запросы каталога требуют developer token; `/v1/me/...` дополнительно требует Music User Token. MusicKit на Apple-платформах и в web может автоматически управлять пользовательским токеном после разрешения пользователя. Для API предусмотрены ответы `401`/`403`; превышение частоты даёт временный `429`.

Для выпуска developer token Apple документирует Media Services private key и прямо говорит, что для запросов Apple Music API разработчик должен быть участником Apple Developer Program. Текущая официальная цена членства — $99 в год (региональные цены могут отличаться). Бесплатная регистрация Apple Developer не равна членству в программе. Поэтому официальный REST-клиент с собственным developer token не подходит под требование «не платить» для индивидуального проекта; локальный Music.app путь ниже остаётся бесплатным кандидатом.

### Публичный iTunes Search API как no-auth matcher fallback

Отдельный legacy endpoint `https://itunes.apple.com/search` принимает обычный HTTP GET без developer token и без Apple Music User Token. В чистой terminal-проверке 27.10.2026 запрос `term=Jack+Johnson&media=music&entity=song&country=us&limit=1` вернул HTTP 200 и JSON с `resultCount` и `results[]`; карточка содержит `trackId`, `trackName`, `artistName`, `collectionId`, `collectionName`, `trackTimeMillis`, `trackViewUrl` и другие store metadata. В этой конкретной карточке поля `isrc` не было. Секреты и пользовательская коллекция не участвовали.

В Chrome открылась официальная архивная страница Apple с тем же endpoint, примерами `term`/`limit`/`entity`/`country` и датой обновления 2017-09-19. Прямой переход в браузере на сам `itunes.apple.com/search` был остановлен как `ERR_BLOCKED_BY_CLIENT`; это browser-side отказ, не HTTP-ответ сервера. Поэтому доступность endpoint подтверждена именно чистым terminal-запросом, а Chrome использовался для проверки официальной схемы и примеров.

Официальная документация Search API находится в архиве Apple (последнее обновление страницы — 2017-09-19), показывает `term`, `entity`, `country` и `limit`, а также обычный JSON результат; максимальные актуальные request/rate limits по найденной официальной странице не установлены. Поэтому отправлять умеренный поток запросов, обрабатывать 429/ошибки и не делать предположений о лимитах. Поиск полезен как бесплатная выдача кандидатов для ручной проверки по названию/артисту/альбому, но отсутствие ISRC и возможность версий/ремастеров делают его менее точным, чем Apple Music API `filter[isrc]`. `trackId` из iTunes Store нельзя без отдельной проверки считать Apple Music catalog ID, пригодным для `/v1/me/favorites` или Library write. Мы не использовали preview/artwork URL и не делали write-запросов; условия Apple ограничивают использование promotional assets, см. [Search API Overview](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/iTuneSearchAPI/).

### Локальный Music.app без MusicKit REST API

Для macOS есть отдельный путь без MusicKit developer token: локальное приложение Music управляется AppleScript. В открытом проекте `ComputerPers/YandexMusic_to_AppleMusic` `add_to_apple_music.py` преобразует Apple catalog URL в `music://`, открывает его в Music.app, запускает текущий трек, дублирует текущую запись в source `Library`, затем ищет её в библиотеке по title+artist и дублирует в плейлист `Yandex Favorites`. При неудаче есть fallback только по title. Заданы ожидания 4+3+2+1 секунд на песню, есть `--from` для продолжения; скрипт печатает имена треков и артистов. README указывает macOS, Music.app и Apple Music account/subscription, но не developer key для этого варианта. В коде нет записи `favorited=true`: итог — Apple Library/обычный плейлист, не Favorite Songs. Это статически просмотренный, незапущенный и неидемпотентный пример Music.app ingestion, а не подтверждённый importer.

Для собственно Favorites опубликован [AppleScript-гист](https://gist.github.com/obitech/5e18ec3c8c24f89c96f0cf396cb33e48); приложенный how-to заявляет MIT. Сам скрипт не входит в Spotify и не делает matching: он ожидает, что Spotify Liked Songs уже перенесены в отдельный плейлист Music.app через Playlisty или аналог. Затем он идёт по плейлисту в обратном порядке, проверяет `favorited`, ставит `true` только ещё не избранным, и ждёт 1 секунду между треками, чтобы сохранить порядок при сортировке Favorite Songs по Date Added. В текущем варианте Script Editor логирует названия и артистов — для нашего локального инструмента это следует убрать или заменить обезличенным прогрессом. Автор заявляет macOS с Music.app и подписку Apple Music; стоимость/условия Playlisty не проверялись. Это сильное подтверждение, что локальная запись Favorite Songs без MusicKit REST технически реализуема, но не доказательство её работы на этой машине, общего matching pipeline или больших/разнородных коллекциях.

Ещё один актуальный референс — [epheterson/applemusic-mcp](https://github.com/epheterson/applemusic-mcp), MIT, проверенный HEAD `3f21259` от 2026-10-23. В README локальный уровень `music` заявляет список Favorites и операции love/unlove через Music.app. В коде список читается AppleScript-процедурой, которая пробует `favorited`, затем `loved`; setter `love_track` записывает `loved`. Установленный на этом Mac SDEF объявляет для track свойство `favorited` (`pLov`), но не `loved`, поэтому совместимость setter с текущей версией Music.app пока не подтверждена и требует безопасного теста на специально выбранной записи.

У проекта различается смысл `love` в зависимости от пути: native Music.app вызывает AppleScript setter, а API path для catalog ID и его fallback вызывают Apple personal rating endpoint. Это не эквивалент официального `POST /v1/me/favorites` и само по себе не доказывает добавление в Favorite Songs. Функция добавления найденного catalog track в Library в просмотренном коде требует network/API path; при `--level music` сетевые запросы запрещены. `--allow-ui` разрешает Accessibility UI actions для сценариев поиска/воспроизведения каталога, но не превращает этот Library add в локальную безтокенную операцию. Поэтому таблицу возможностей README нельзя принимать как доказательство бесплатного полного импорта без отдельной проверки. Web/API режимы и browser token flow в этот бесплатный сценарий не включать.

Практически сверил системный словарь Music.app на этом Mac: `/System/Applications/Music.app/Contents/Resources/com.apple.Music.sdef`. Для класса `track` он объявляет `favorited` (`pLov`) как boolean с доступом на чтение и запись; `database ID`, `artist`, `album`, `duration`, `track number` и `disc number` доступны как свойства трека, причём постоянный database ID read-only. В словаре также есть команда `search` по тексту внутри переданного playlist и команда `add` с входом типа file — добавление произвольных локальных файлов в playlist/library. Это не описывает поиск каталога Apple Music по ISRC и не доказывает добавление cloud-catalog ID из AppleScript.

Терминальная read-only проверка `osascript` на этом Mac подтвердила чтение `favorited` у существующего трека и выполнение запроса `count of (every track whose favorited is true)`. Вывод содержимого/числа библиотеки подавлялся; ни одно название или количество не записано, состояние треков не менялось. Простая форма `count of tracks whose favorited is true` ошиблась в AppleScript, а форма со скобками вокруг списка сработала. В этой проверке SDEF XML из bundle подтвердил, что track-класс имеет read/write automation access, а `favorited` — boolean property с кодом `pLov`. Отдельный скрипт `set favorited of track 1 of library playlist 1 to true` успешно скомпилирован `osacompile` из временного файла, который удалён; сам Apple Event не запускался. Это подтверждает синтаксис/термин, но не успешную live-запись, разрешение Automation, облачную синхронизацию или поведение для конкретного каталожного трека. Совместимость стороннего setter с именем `loved` не доказана. Цепочка «найти каталоговый трек → добавить его в облачную Library → выставить Favorite» пока не подтверждена целиком.

Рабочая гипотеза для бесплатного локального мигратора: выгрузить лайки провайдера → сопоставить с каталогом Apple → добавить найденные записи в Library/временный плейлист через штатное Music.app управление → локальным AppleScript выставить Favorites → сверить результат и отчёт пропусков. Ограничение Apple Developer Program относится к REST API и не автоматически к AppleScript. Сценарий всё равно требует Apple Music subscription и локального Mac; массовую запись, облачную синхронизацию и поведение на уже добавленных/недоступных треках нужно проверить на тестовой небольшой выборке.

### Ещё один Apple Music backup-кандидат: userscript

[pinyht/apple-music-transfer](https://github.com/pinyht/apple-music-transfer), MIT, версия 1.0.4 (commit `296e59e`, 2026-03-09), — Tampermonkey script для экспорта/импорта songs, albums и playlists в JSON/CSV. В исходнике он перехватывает ответы `amp-api.music.apple.com/v1/me/library/songs` и `/albums`, восполняет пропущенные страницы параметрами `offset`/`limit` и экспортирует для песни `id`, `name`, `artistName`, `albumName`. Для библиотечных плейлистов скрипт читает элементы через видимую страницу и скроллинг.

Это backup/restore Apple Library, не мигратор лайков: в экспортируемой структуре песен нет поля `favorited`, а README не заявляет экспорт или восстановление Favorite Songs как флага избранного. Songs API вызывается с `credentials: include` в контексте авторизованного `music.apple.com`; это использует существующую web-сессию, а не отдельный публичный OAuth flow. Скрипт может дополнить наш будущий Apple backup/import path, но перед применением надо вручную ревьюить полный userscript и сначала проверять небольшую выборку.

Дополнительный статический аудит pinned script: `@match` ограничен `https://music.apple.com/*`, `@grant none`, сторонних `@require` нет. Код оборачивает `window.fetch`, `Response.json/text` и `XMLHttpRequest`, но собиратель распознаёт только `amp-api.music.apple.com/v1/me/library/songs` и `/albums`; экспорт песен восполняет пропущенные `offset`/`limit` страницы, импорт вызывает штатные кнопки Apple Music для Library и плейлистов. Поиск URL и сетевых вызовов не обнаружил endpoint передачи библиотеки на другой домен; это статический вывод по checkout, не динамическая сетевая проверка. Очередь импорта, прогресс и логи сохраняются в `localStorage` origin `music.apple.com`, а диагностический `console.log` печатает artist/album названия для matching score. Для нашего продукта это аргумент за явно очищаемый локальный job state и обезличенный лог; сам скрипт не запускали.

### CLI-кандидат для переноса между Apple ID: `bit-of-a-shambles/apple-music-transfer`

В репозитории [`bit-of-a-shambles/apple-music-transfer`](https://github.com/bit-of-a-shambles/apple-music-transfer/tree/d610e2489ed20153bbb22fc4d4a557eb59451dd5) (HEAD `d610e24`, 2026-03-15) найден локальный Python CLI: читает `Library.xml` старого Apple ID, открывает MusicKit authorization для нового аккаунта и затем ищет песни в Apple catalog, добавляет их в Library и пересоздаёт playlists. GitHub license metadata отсутствует, в дереве нет `LICENSE`; код не заимствовать без уточнения прав.

Source перечисляет запросы `GET /v1/me/storefront`, `GET /v1/catalog/{storefront}/search?term=…&types=songs&limit=5`, `POST /v1/me/library?ids[songs]=…` пачками по 25, `POST /v1/me/library/playlists` и `POST /v1/me/library/playlists/{id}/tracks`; dedup helper читает `GET /v1/me/library/songs?limit=100` и проходит `next`. Авторизация запускает loopback HTTP server на `127.0.0.1:8754`, генерирует Apple developer JWT из личного `.p8`, загружает MusicKit JS, вызывает `music.authorize()` и возвращает Music User Token в callback query `?token=…`. Это простой вход на сайте Apple, но требует авторских/пользовательских paid Developer credentials и переносит токен в URL/историю браузера; production flow так не проектировать.

Этот проект не покрывает Spotify/Яндекс/Звук и не пишет в `/v1/me/favorites`: destination — обычная Apple Library и плейлисты. Matcher ищет по названию + артисту, затем берёт первый результат как fallback; ISRC и review перед записью нет. Состояние `transfer_state.json` позволяет продолжить процесс, но не делает read-back после library write. Отдельный `dedup_playlists.py` удаляет одинаковые по имени playlists через AppleScript без dry-run; его нельзя запускать на пользовательской Library в рамках проверки. Точная реализация ценна как референс MusicKit user authorize → localhost callback и Library endpoints, не как готовый бесплатный Favorite Songs importer. Только статический анализ README/source; ни auth, ни аккаунт, ни write не запускались.

### Встроенный перенос в Apple Music

Apple поддерживает пользовательский transfer flow в приложении и на `music.apple.com`. Актуальная [Apple Support инструкция для региона AE](https://support.apple.com/en-ae/118249), опубликованная 31.03.2026, говорит: нужны Apple Music subscription и включённая Sync Library; пользователь входит в выбранный source service; liked/loved songs должны попасть в Favorite Songs; перенос не удаляет исходные записи. Что именно переносить, решает каждый source service — доступность всего каталога, плейлистов и favorites может отличаться. Apple называет transfer сторонней услугой, но не публикует её провайдера, endpoint/API, цену, квоту или гарантии полноты; поэтому пока нельзя обещать, что эта возможность бесплатна и безлимитна.

Если Apple не находит точное совпадение, пользователь может просмотреть альтернативы в течение 30 дней; до завершения этого review новый transfer на том же устройстве не стартует. Переносятся только playlists, созданные пользователем, не автоматические playlists самого music service. Apple указывает, что transfer недоступен в материковом Китае, Мьянме и России; для UAE региональная инструкция опубликована, но список источников всё равно определяется фактическим UI/account. Это сильный zero-setup candidate для первого ручного Spotify → Apple теста, если Spotify показывается в списке; источник Яндекс/Звук не подтверждён. В нашей предыдущей live UI-проверке меню открылось, но показало **Transfer Service is Busy**, поэтому ни список сервисов, ни перенос не проверены.

Live UI-проверка в текущей авторизованной вкладке: пункт **Transfer Music** присутствует в меню аккаунта. Повторная проверка 27.10.2026 показала оболочку **Select a Music Service**, но внутри — **Transfer Service is Busy**; список источников не отрисовался. Spotify, Яндекс и Звук для этого аккаунта этим наблюдением не подтверждены и не опровергнуты. Flow не дошёл до авторизации стороннего сервиса и переноса.

## Каталог, библиотека, избранное

- ISRC-first поиск: `GET https://api.music.apple.com/v1/catalog/{storefront}/songs?filter[isrc]=<isrc>`; документация задаёт максимум 25 ISRC на запрос, но один ISRC может вернуть несколько каталоговых записей. Результаты надо дополнительно сверять по версии, артисту, альбому и длительности.
- Обычный текстовый поиск: `GET /v1/catalog/{storefront}/search?term=<query>&types=songs,albums,artists`; доступен `limit`, затем совпадение проверяется по метаданным.
- Чтение библиотеки: `GET https://api.music.apple.com/v1/me/library/songs`; требует Music User Token вместе с developer token в официальном API, поддерживает `limit`/`offset` и возвращает `next`, который надо читать до отсутствия. Это все library songs по алфавиту, не отдельный список Favorites. Для catalog ID в library response может присутствовать `playParams.catalogId`.
- Просмотр Favorite Songs: в официальной документации найден write endpoint `POST /v1/me/favorites`, отдельный публичный `GET /v1/me/favorites` не обнаружен. Для read-back используется системный Favorite Songs playlist из `/v1/me/library/playlists` и его relationship `/tracks`; live Chrome/terminal GET этого плейлиста и одного item ранее подтвердил `200`. Account-specific playlist ID не сохранять.
- Добавление в Favorite Songs: `POST https://api.music.apple.com/v1/me/favorites?ids[songs]=<catalog-id>` с developer + music user authorization. Документация указывает `202 Accepted`; если пользователь favorites song, она добавляется в `favorite songs` playlist. Недоступные IDs могут быть проигнорированы, поэтому успех HTTP сам по себе не равен успешному импорту. API разрешает bulk additions; проверенные сторонние проекты отправляют по одному треку.
- Создание обычного плейлиста: `POST /v1/me/library/playlists`, добавление элементов в playlist поддерживается отдельно. Это не эквивалент добавлению в favorites.
- Добавление ресурса в библиотеку `POST /v1/me/library` — отдельная операция от `/me/favorites`; нужно не смешивать понятия «в библиотеке» и «избранное».
- Отдельный personal rating API: `PUT /v1/me/ratings/songs/{catalog-id}` с `{ "type": "rating", "attributes": { "value": 1 } }` устанавливает оценку «нравится» (`1`; dislike `-1`); `GET` читает, `DELETE` убирает эту оценку. Документация описывает это как song rating, а не добавление в Favorite Songs. Не считать `rating=1` эквивалентом `favorited=true` без отдельного read-back через Favorites.
- Это различие встретилось в свежем `nedu-m/spotify-to-apple-music`: команда называется `favourite`, но вызывает `PUT /me/ratings/songs/{id}`. Apple официально описывает отдельный `POST /v1/me/favorites?ids[songs]=...`, который добавляет песню в `favorite songs` playlist. Music.app SDEF также объявляет независимые свойства `rating` и boolean `favorited`.

### Дополнительный Apple write-кандидат: bootleg

В MIT Go-проекте [moudlajs/bootleg](https://github.com/moudlajs/bootleg) (HEAD `a384ff52`, 2026-10-18) локальный CLI умеет искать Apple catalog songs из текстового файла, показать dry-run и затем писать в playlist, Library или Favourite Songs. Статический просмотр `internal/applemusic/library.go` показывает, что `Favorite()` вызывает именно `PUT /v1/me/ratings/songs/{catalog-id}` с `attributes.value=1`; официальный контракт этого endpoint говорит только о rating «likes», тогда как отдельный `POST /v1/me/favorites` прямо обещает включить песню в `favorite songs` playlist. Значит слово Favourite в CLI пока не подтверждает нужное нам Apple-состояние; нужен read-back через Favorite Songs после одного тестового трека, но тестовую запись здесь не делали.

Для Apple авторизации bootleg просит вручную скопировать из DevTools web-player `authorization` (developer token) и `media-user-token` в локальный `.env`. Это убирает собственный developer key, но остаётся частным web-player contract, копированием двух секретов и периодическим обновлением user token. Hosted MCP-вариант требует самостоятельной облачной установки, поэтому проще и безопаснее изучать локальный CLI как кодовый reference, а не запускать remote connector. В коде HTTP client задаёт оба токена заголовками, `Origin: https://music.apple.com` и редактирует их из `String`/`slog`; дополнительно проверить всю поверхность логирования до заимствования.

### Локальный Favorite/import reference: `Skalas/music-sync`

Статически просмотрен [pinned commit `9f961d9`](https://github.com/Skalas/music-sync/tree/9f961d9e439885eaff6dff6da125e238f278da6e) от 2026-10-09. `applescript/read_loved.applescript` перечисляет треки Music.app с `favorited is true` и fallback на старое `loved`; `mark_loved.applescript` ищет сначала по названию + исполнителю, при нуле результатов повторяет поиск только по названию, затем выставляет `favorited=true` (fallback `loved=true`). Такая операция не требует Apple REST developer token, но title-only fallback может выбрать не ту версию песни и нуждается в review/строгом матчинге.

Для треков, которых ещё нет в локальной Library, provider вручную запускает Shortcut `SyncToAppleMusic`: он ищет в iTunes Store по тексту с лимитом результата `1`, добавляет выбранную запись в Library, после чего проект повторно перечитывает Music.app и отмечает только проверенные совпадения как Favorites. Это конкретная реализация локальной цепочки `Library add → favorited`, но Shortcut надо создать вручную; каталоговый поиск и запись здесь не выполнены через официальный Favorites REST API. README описывает local FastAPI + TypeScript dashboard, `make dev`, три экрана Connections/Library/Actions и dry-run по умолчанию; для Spotify требуется собственная OAuth app, Tidal необязателен, Яндекс/Звук отсутствуют. MusicKit `.p8` нужен лишь для точных каталоговых links/metadata в этом проекте, не для локального AppleScript setter.

GitHub license metadata у репозитория отсутствует, в проверенном checkout файла `LICENSE` нет. Исходник и UI просмотрены статически; приложение, Shortcut, account auth и live favorite writes не запускались. Поэтому это ценная независимая демонстрация, что локальный setter правдоподобен, но не доказательство успешного массового импорта или облачной синхронизации на нашей машине.

На текущем macOS `osacompile` успешно скомпилировал оба сторонних скрипта `read_loved.applescript` и `mark_loved.applescript` против установленного словаря Music.app; временные `.scpt` артефакты удалены после проверки. Скрипты не запускались. Это закрывает только синтаксис/терминологию текущего AppleScript environment, не Automation permission, поиск совпадений, setter runtime, Library import или iCloud/Apple Music sync.

### Наблюдаемая авторизация Apple Music web player

В текущей авторизованной вкладке `music.apple.com` сетевые запросы к `amp-api.music.apple.com` несут заголовки `Authorization: Bearer …` и `Media-User-Token: …`. Это web-player пара токенов, полученная штатным клиентом сайта; она технически отличается от созданного нами developer JWT, хотя API использует тот же HTTP Bearer заголовок. Не выдавать её за документированный сторонний OAuth flow.

По прямому разрешению владельца аккаунта эту пару временно использовали в чистом терминальном HTTPS-клиенте только для чтения:

- `GET /v1/me/library/playlists?limit=1` → `200`, JSON с `data`, `meta`, `next`.
- `GET /v1/me/library/playlists/{favoritePlaylistId}/tracks?limit=1` для системного Favorite Songs → `200`, `data` типа `library-songs`, доступны поля вроде `name`, `artistName`, `albumName`, `durationInMillis` и `playParams`; присутствовал `next`.
- В распакованном JWT без сохранения самого значения были claims `exp`, `iat`, `iss`, `root_https_origin`; при захвате срок до `exp` был около 63 дней. Это конкретная сессия, не гарантия срока для других токенов.

Токены хранились только в одноразовом файле с mode `0600`, файл удалён сразу после каждого запроса; ответ обработан в памяти, названия и ID треков не записывались. Предыдущая проба с одним только `media-user-token` без bearer дала `401`; web-player bearer вместе с ним дал `200`. Это доказывает работоспособность конкретного чистого GET сейчас, но не даёт стабильной публичной авторизации. Никаких POST/DELETE к Apple не посылали.

## Практическая проверка

- В авторизованной вкладке Music Web для storefront `tr` при открытии видимого раздела избранного браузер получил `200` от `GET https://amp-api.music.apple.com/v1/me/library` и `GET /v1/me/library/playlists/{id}`; запрос каталога `GET /v1/catalog/tr` также вернул `200`. Это подтверждает работу сессии веб-приложения в браузере, но не выдаёт поддерживаемый публичный способ получать его credentials.
- Из терминала без пользовательской авторизации `GET https://api.music.apple.com/v1/me/library/songs?limit=1` и поиск `GET /v1/catalog/us/search?...` вернули `401`. Официальный REST-доступ требует developer token, а пользовательские `/me` операции — ещё и Music User Token.
- Повторная чистая terminal-проверка только с `media-user-token` из Chrome cookie, но без Authorization bearer, вернула `401` на `/v1/me/library/songs?limit=1`. Отдельная проверка выше с парой заголовков, скопированной по live-запросу web player, вернула `200` на список плейлистов и один элемент Favorite Songs.
- Словарь установленного локального Music.app (`com.apple.Music.sdef`) объявляет свойство `favorited` как read/write для треков; persistent ID доступен только для чтения. Это локальное AppleScript-поверхностное API, отдельное от MusicKit REST. Оно делает локальный сценарий правдоподобным, но полноценную запись избранного ещё надо безопасно проверить на тестовом наборе.
- Запись через браузерные или REST endpoints не выполнялась; account identifiers, playlist ID и содержимое коллекции в документацию не переносились.

## GitHub cross-check: Yandex Music Transfer → Favorite Songs

В актуальном на 27.10.2026 MIT checkout [`yarikmsu/yandex-music-transfer`](https://github.com/yarikmsu/yandex-music-transfer/tree/eb883666a05594fa76d2e2620aff27b169b1700c) статически прослежен destination flow. Live import не запускался, пользовательский Apple аккаунт не менялся:

| Шаг | Запрос / поведение в проверенном source |
|---|---|
| Узнать storefront | `GET https://amp-api.music.apple.com/v1/me/storefront` |
| Найти кандидатов | `GET https://itunes.apple.com/search?term=…&country={storefront}&media=music&entity=song&limit=10`; без токенов. Результат преобразуется в Apple song-shaped object по `trackId`, title, artist, album и duration; не-streamable записи исключаются. |
| Создать необязательные плейлисты | `POST /v1/me/library/playlists`, затем `POST /v1/me/library/playlists/{id}/tracks` с пачками до 50 catalog IDs. |
| Добавить в Favorite Songs | `POST https://amp-api.music.apple.com/v1/me/favorites?ids[songs]={catalog-song-id}`; source отправляет по одному song ID в запросе. |

Apple документирует аналогичный `POST https://api.music.apple.com/v1/me/favorites`, параметр `ids` по типу ресурса, ответ `202 Accepted` без тела и возможность bulk добавления heterogeneous resources. Apple также предупреждает, что ID, которые нельзя добавить в библиотеку, просто игнорируются. Поэтому один ID на запрос в данном importer — решение его реализации, не установленный публичный лимит Apple. Его `state.json` дописывает ID после успешного HTTP-ответа, но код не перечитывает Favorite Songs и не подтверждает каждый каталоговый ID через read-back; после `202` считать перенос доказанным нельзя. Наш importer должен сверять фактический Favorite Songs список с планом.

Авторизация этого кандидата не является входом через официальный third-party OAuth: он вручную принимает web-player `Authorization` bearer и `Media-User-Token` в env-файле, отправляет их на `amp-api.music.apple.com` и предупреждает, что Apple не поддерживает такой сценарий. Это полезная проверка destination route и matching-пайплайна, но не шаблон UX «просто войти». Docker-контейнер ограничен read-only filesystem/privileges и отдельной writable `out/` папкой; токены остаются в локальном env-файле, поэтому этот файл нужно считать отзывным credential и никогда не коммитить.

Из checkout запущен upstream offline unittest suite: `python3 -B -m unittest` — 209 тестов прошли (`OK`) на Python 3.15. Это unit tests с mock-ответами, а не проверка Apple/Yandex endpoints или реализации в Docker. Docker CLI в текущем окружении отсутствует, поэтому задокументированная upstream контейнерная команда здесь не проверена; несколько `ResourceWarning` о закрытии синтетических `HTTPError` появились в тестовом выводе.

## Ограничения для миграции

Нужен storefront пользователя: каталожные ID региональны, некоторые записи отсутствуют или доступны только в другом storefront. Favorite request может игнорировать неразрешимые ID без подробного результата по каждому элементу, поэтому после пачек требуется повторно перечитать Favorite Songs/библиотеку и сравнить фактический набор. API не переносит исходный аудиофайл и не гарантирует точное соответствие версии/ремастера.
