# Авторизация и архитектура сессий музыкальных сервисов

Проверено по коду проекта и документации поставщиков на 2026-10-28. Этот документ различает поддерживаемые публичные API и запросы, которые видны только внутри веб-клиента сервиса. Наличие работающего внутреннего endpoint не означает, что сервис поддерживает сторонний API или гарантирует его стабильность.

## Краткий вывод

Для Apple Music и Spotify существуют официальные API для пользовательских библиотек и плейлистов. Они требуют идентификатор приложения и пользовательское разрешение; Apple также требует подписанный Developer Token. Такой путь может выполнять запросы из приложения и не требует постоянно открывать сайт музыкального сервиса, но не соответствует ограничению «без приложения/учётных данных владельца проекта».

Текущие коннекторы Яндекс.Музыки и Сбер.Звука используют browser-session endpoints, которые не документированы как публичные API для сторонних импортёров. Их безопасный и фактически применяемый контекст — страница соответствующего сервиса, где пользователь уже вошёл. Для надёжного сценария со всеми четырьмя сервисами расширение поэтому оставляет страницы сервисов открытыми в фоне. Это не отдельные окна и обычно не требует действий после входа, но закрывать страницу во время текущего чтения/записи нельзя.

## Как текущая версия использует страницы и сессии

Manifest внедряет readers в страницы доменов сервисов (`chrome-extension/manifest.json`, content scripts), а worker адресует сообщения соответствующей вкладке через `chrome.tabs`. Основная логика открытия вкладок и сбора находится в [`service-worker.js`](../chrome-extension/service-worker.js#L537) и [`app.js`](../chrome-extension/app/app.js#L1426). Сайт сам выполняет обычный вход пользователя; приложение не просит пароль и не читает Chrome cookie jar. Apple и Spotify держат наблюдаемые заголовки только внутри page-script closure; Яндекс использует обычные browser credentials при `fetch`; Звук повторяет запрос страницы в её origin. Через bridge приложению передаются нормализованные треки и плейлисты, не сессионные заголовки.

### Что должен увидеть пользователь при обычном входе

1. Music Importer проверяет доступные аккаунты. Уже авторизованные сервисы читаются в фоновых вкладках, а результат и прогресс видны в карточках сервисов.
2. Если сервис не авторизован, его карточка сообщает, что библиотека недоступна, и показывает действие **«Войти / открыть»**. Нажатие открывает или активирует обычную страницу сервиса; пользователь проходит штатный вход непосредственно у поставщика.
3. После входа пользователь возвращается в Music Importer. При возвращении приложение повторно проверяет сессию и начинает сбор доступной библиотеки: likes, каталог плейлистов и их позиции/треки там, где reader поддерживает эти данные.
4. Сервисные страницы могут оставаться в фоне. Они нужны текущим адаптерам для браузерной сессии и выполнения запросов от имени вошедшего пользователя; их не требуется вручную открывать, если вход уже есть. Во время незавершённого сканирования или записи соответствующую вкладку нужно оставить открытой. Перезапуск/закрытие вкладки во время операции может прервать работу; полноту должен подтверждать статус приложения.

Формулировка «после входа сразу подтянутся все каталоги» применима только к сервисам, где reader завершил чтение и подтвердил полноту. Это не гарантия, что у каждого аккаунта все страницы уже авторизованы или что приватный API не изменился. Текущий проект отдельно документирует live-ограничения и не считает fixture tests подтверждением live-переноса: см. [матрицу возможностей](TRANSFER_CAPABILITY_MATRIX.md).

## Практическое решение для tab-less режима

- Для Apple Music можно исследовать отдельный MusicKit JS adapter. Это поддерживаемый API-путь, но до его реализации потребуются Media Services identifier, Apple private key и безопасное место для выпуска Developer Token. Приватный ключ не должен попадать в GitHub Pages или Chrome extension package.
- Для Spotify можно исследовать OAuth PKCE adapter, зарегистрированный на конкретное приложение. Перед разработкой нужно подтвердить возможность использовать client ID, redirect URI и Development Mode ограничения для предполагаемой аудитории. OAuth не требует хранить client secret в расширении, но не отменяет регистрацию приложения и получение user consent.
- Для Яндекс.Музыки и Звука оставлять текущие адаптеры отдельным compatibility layer и считать их best-effort, пока поставщики не предоставят документированные API/официальную авторизацию. Не маскировать внутренние endpoint-ы под публичную интеграцию и не просить пользователя вручную копировать токены.
- До изменения архитектуры можно уменьшить заметность текущего tab-bound подхода: открывать и активировать только выбранный источник/цель при входе, держать уже авторизованные сервисы фоном, показывать отдельный статус по каждому аккаунту и точную причину отказа. Полностью отказаться от provider tabs без изменения auth/API пути нельзя обещать.

## Источники и пределы вывода

Официальные ссылки в разделах Apple и Spotify описывают API/auth модели, а не подтверждают работу именно этого проекта. Приватные endpoint-ы установлены по текущим исходникам и исследованиям проекта; они не являются гарантией поставщика. Состояние пользовательских аккаунтов и сессионные данные для написания документа не читались.
