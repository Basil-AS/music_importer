# GitFlow и фиксация результатов

Для этого проекта всегда используем GitFlow. Промежуточные и итоговые результаты, которые меняют рабочее дерево, фиксируем отдельными осмысленными коммитами. Не оставляем выполненную работу незакоммиченной в конце этапа.

## Ветки

- `master` — стабильная основная ветка.
- `develop` — интеграционная ветка разработки.
- `feature/<краткое-имя>` — новая функциональность или исследование; ответвляется от `develop` и после завершения вливается обратно в `develop`.
- `release/<версия>` — подготовка релиза от `develop`; после проверки вливается в `master` и обратно в `develop`.
- `hotfix/<краткое-имя>` — срочное исправление от `master`; после исправления вливается в `master` и `develop`.

Префикс `ai/` или `agent/<имя>/` можно добавить к имени ветки, если это нужно для фильтрации автоматизацией, сохраняя назначение ветки GitFlow, например `feature/ai/music-import`. Не коммитить работу задачи напрямую в `master` или `develop`.

Если к началу задачи ветки `develop` ещё нет, создать её от основной ветки проекта, затем начать feature-ветку от `develop`. Перед началом работы проверить активную ветку, чистоту дерева и актуальность базовой ветки.

## Коммиты и раскрытие использования ИИ

- Использовать короткие Conventional Commit заголовки, например `docs: document provider authorization`.
- Если агент существенно создал содержимое коммита, добавлять в тело:

  ```text
  Generated-by: OpenAI Codex (GPT-6)
  Co-authored-by: Codex <noreply@openai.com>
  ```

- Если человек создал результат, а ИИ только помогал, использовать `Assisted-by:` вместо `Generated-by:`. Не указывать выдуманные ID задачи, модельные метаданные или статус проверок.
- Коммитить логически завершённые этапы по мере выполнения, а не только в конце задачи. Перед каждым коммитом посмотреть diff и включить только относящиеся к работе файлы.
- Не переписывать и не включать в свои коммиты чужие изменения без отдельного основания.
- Не коммитить cookies, access/refresh tokens, пароли, секреты приложений, HAR с авторизационными заголовками и реальные пользовательские экспорты. Для локальной проверки использовать исключённые из git secret/config файлы или переменные окружения; перед фиксацией проверять staged diff.
- Глобальный Git author для Basil-AS: `user.name=Basil-AS`, `user.email=71924962+Basil-AS@users.noreply.github.com`. В коммитах агент указывается вторым автором через `Co-authored-by: Codex <noreply@openai.com>`; этот email является GitHub-распознаваемой идентичностью Codex.
- Chrome можно использовать для проверки видимого состояния сайтов и пользовательских сценариев. Не читать browser cookies, local storage, профили, пароли и session stores; не извлекать значения токенов из запросов. Для технических заметок сохранять только несекретные наблюдения интерфейса и документированные API.

Для этой задачи пользователь поручил вести GitFlow, коммитить промежуточные результаты, регулярно отправлять feature-ветку и поддерживать PR в `develop`; это разрешение действует на последующие итерации исследования.
