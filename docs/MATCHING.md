# Массовое сопоставление треков

Прототип содержит provider-neutral модуль `demo/matcher.js`. Он сравнивает нормализованные метаданные источника с результатами каталога назначения. Экспериментальные catalog search adapters подключены для Apple Music, Spotify, Яндекс Музыки и Звука. Кнопка массового сканирования сначала читает библиотеки всех открытых авторизованных вкладок; выбранный target catalog searches затем для каждого трека.

## Порядок решения

1. Если ISRC есть на обеих сторонах и совпадает после нормализации, это точный кандидат.
2. Иначе считаются похожесть названия и исполнителя; альбом и длительность добавляют evidence, когда присутствуют с обеих сторон.
3. Маркеры версии записи (`live`, `remix`, `remaster`, `acoustic`, `radio edit`, `sped up`, и др.) предотвращают автоматическое принятие несовпадающих версий.
4. Метаданные автоматически выбираются только при score не ниже `0.96` и отрыве от следующего кандидата не меньше `0.035`; иначе запись направляется на ручную проверку.

Эти пороги — консервативный старт, а не измеренная точность. Их нельзя считать доказанными для тысяч записей, каталогов всех четырёх сервисов, кавер-версий, одинаковых названий, фичерингов и региональных вариантов. Перед включением записи в аккаунт нужно собрать обезличенные labeled fixtures из пользовательских решений, измерить precision отдельно по языкам/версиям и настроить порог так, чтобы ошибочный перенос был редким. Неизвестные и неоднозначные записи должны оставаться в review queue.

## Массовая обработка

`demo/transfer-engine.js` содержит общий `searchMany(adapter, tracks)`: он объединяет одинаковые поисковые запросы и ограничивает параллелизм настройкой адаптера. Там же есть `discoverAllCollections()` и `readLibrary()`: engine проходит страницы обнаружения коллекций, затем читает каждую найденную favorites/playlist коллекцию до конца и собирает единый snapshot. `readCompleteCollection()` останавливается при повторе cursor, дедуплицирует favorites по provider ID, сохраняет повторные playlist items и позиции, сверяет `totalCount` и принимает checkpoint callback после каждой страницы. Без независимого total подтверждённость snapshot остаётся `false`. `transfer-core.createSnapshot()` поддерживает несколько коллекций одного аккаунта.

Массовый поиск выполняется с ограниченной параллельностью и объединяет дубликаты запроса; точность, скорость, provider rate limits и поведение на тысячах записей ещё не измерены. Автоподбор остаётся консервативным (точный ISRC или высокая metadata confidence с отрывом от следующего кандидата); остальные случаи остаются в review queue. Для автоматического массового импорта нужна labeled-проверка качества на реальных наборах, прежде чем снижать пороги. Каждый adapter передаёт исходный provider ID, ISRC, нормализованные credits, версию, длительность, storefront и provenance, а также сохраняет порядок и повторы playlist items.

Чтобы массовый список не перегружал интерфейс, экран сверки показывает 50 строк за страницу и позволяет отфильтровать записи без уверенного совпадения. Поиск обновляет прогресс группами запросов, а не перестраивает весь DOM после каждого трека. Это снижает нагрузку от UI, но само по себе не доказывает, что целевые сервисы выдержат тысячи поисковых запросов: лимиты и скорость каждого каталога нужно измерить отдельно.

## JSON-план

Каждая выбранная запись сохраняет provider ID, ISRC, название, исполнителей, альбом, длительность, исходный playlist ID и позицию. Блок `match` содержит метод, confidence и признак auto-match. Общая модель и builder плана находятся в `demo/transfer-core.js`: snapshot содержит несколько коллекций источника с отдельной полнотой, а план `music-transfer-plan` отдельно задаёт источник, назначение и нативную операцию `add_to_favorites` или `add_to_playlist`. Движок допускает любой из четырёх provider IDs как source/target; для каждого есть поиск и writer с fixture coverage, но live-трансфер не проверен.
