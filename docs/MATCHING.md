# Массовое сопоставление треков

Прототип содержит provider-neutral модуль `demo/matcher.js`. Он сравнивает нормализованные метаданные источника с результатами каталога назначения. Экспериментальные catalog search adapters подключены для Apple Music, Spotify, Яндекс Музыки и Звука. Кнопка массового сканирования сначала читает библиотеки всех открытых авторизованных вкладок; выбранный target catalog searches затем для каждого трека.

## Порядок решения

1. Если ISRC есть на обеих сторонах и совпадает после нормализации, это точный кандидат. Если каталог вернул несколько записей с этим ISRC, безопасная версия без конфликта по `live`/`remix`/другим маркерам получает приоритет; если подходит только конфликтующая версия, трек остаётся на ручной проверке. Для поиска Apple Music и Spotify сначала используется `isrc:...`; при отсутствии точного ответа поиск повторяется по названию и исполнителю. Для Яндекс Музыки и Звука используется доступный полнотекстовый поиск, затем ISRC сравнивается в кандидатах, если сервис его вернул.
   Перед запросом каталога приложение также проверяет полный снимок подключённого аккаунта назначения. Если точный ISRC уже есть в лайках или любом считанном плейлисте, используется ID этой записи и сетевой поиск для неё пропускается. Если ISRC нет, среди записей того же нормализованного названия (включая безопасную транслитерацию) берётся только кандидат, который проходит общий строгий порог matcher; неоднозначные варианты идут на сетевой поиск. Это уменьшает число запросов и помогает избежать повторных лайков; оно не заменяет поиск по каталогу для отсутствующих в библиотеке записей. Такие результаты не записываются в долговременный кэш, поскольку ID могут быть привязаны к конкретному аккаунту. Для Apple Music локальный shortcut использует только catalog ID из `playParams`, `catalogId` или связи `relationships.catalog`, а не ID library-объекта.
   Индекс аккаунта хранит для названия исходную форму и вариант без `feat.`/`featuring`/`ft.`-кредита, включая транслитерированные ключи. Поэтому один и тот же трек может быть найден в уже просканированной цели, когда один сервис включает приглашённого артиста в название, а другой показывает его отдельным исполнителем. Если обе стороны явно называют разных приглашённых артистов, автоподбор запрещён и запись остаётся на ручную проверку. Само решение проходит прежние проверки названия, исполнителей, версии, альбома и длительности: нормализация ключа только находит кандидатов и не снижает порог автоподбора.
   Синтетические проверки индекса разрешают по 10 000 треков с точным ISRC и без ISRC для каждого из четырёх сервисов, если записи уже присутствуют в полном целевом снимке аккаунта; такие записи не требуют отдельного catalog-search запроса. Проверка без ISRC требует точных названия, артиста, альбома и длительности, чтобы не принимать неоднозначную версию автоматически. Это подтверждает работу локального индекса на больших синтетических наборах, но не live-замер точности на пользовательских библиотеках, доли пригодных метаданных или лимитов сетевых каталогов.
2. Каталоговый запрос по умолчанию включает название, исполнителя и альбом. Если выдача пуста либо ни один кандидат не проходит безопасный порог автоматического выбора, приложение ищет шире: по названию и исполнителю, затем по латинской транслитерации. Для Яндекс Музыки и Звука оно также пробует кириллический вариант распространённой латинской транслитерации, только если обратное преобразование совпадает с исходным написанием. Кандидаты объединяются без дублей и повторно ранжируются. Ручной поисковый запрос не переписывается и не расширяется. Затем считаются похожесть названия и исполнителя; альбом и длительность добавляют evidence, когда присутствуют с обеих сторон.
3. Маркеры версии записи (`live`, `remix`, `remaster`, `acoustic`, `radio edit`, `sped up`, и др.) предотвращают автоматическое принятие несовпадающих версий. Синонимы вроде `remaster`/`remastered` сводятся к одной категории. Метки издания альбома (`Deluxe`, `Anniversary Edition`) не считаются отличиями записи сами по себе, поскольку могут отсутствовать в одном каталоге при той же фонограмме.
4. Метаданные автоматически выбираются только при score не ниже `0.96` и отрыве от следующего кандидата не меньше `0.035`. Почти равные кандидаты можно считать дублями одной записи, если у них общий подтверждённый ISRC либо ISRC отсутствует у всех, а название, основной артист, альбом и длительность (разница до 2 секунд) точно совпадают и версия записи не конфликтует. Тогда выбирается лучший ранжированный ID. Разные ISRC, несовпадающие альбом/длительность или противоречащие метки версии сохраняют ручную проверку.

Для сравнения названий и исполнителей выполняется прямое сравнение и дополнительная транслитерация кириллицы (русские, украинские и белорусские буквы). Обёртки с `feat.` удаляются только из названия трека; версия записи проверяется по исходному названию. Это помогает находить, например, «Время» и `Vremya`, не снижая порог автоматического выбора. Для поиска в Яндекс Музыке и Звуке латинская форма может быть преобразована обратно в кириллицу, только если обратный проход через ту же таблицу даёт исходную форму. Транслитерация — дополнительный сигнал, а не гарантия правильности; точность на реальных библиотечных данных ещё не измерена.

Список артистов сравнивается в обе стороны, когда оба каталога перечисляют несколько имён: несовпадающие полные кредиты удерживают результат от автоматического выбора. Если один каталог указывает только основного исполнителя, а другой также указывает гостевого, отсутствие дополнительного имени само по себе не снижает score. Это покрывает разницу в полноте credits, не меняя строгий порог автоматического выбора.

Все успешные результаты каталога (до 12 нормализованных кандидатов или подтверждённое отсутствие выдачи) кэшируются в IndexedDB локальной страницы: совпадения до 30 дней, пустая выдача 7 дней, не более 25 000 записей. Ключ учитывает целевой сервис, storefront и режим Apple Music (public preview или account catalog), ISRC либо полные метаданные. Для Яндекс Музыки сохраняется album ID, необходимый для создания плейлиста. Ошибки сети и ручные поисковые запросы не кэшируются. Cookies, tokens, playlist membership и исходная библиотека не сохраняются. Кэш можно очистить в интерфейсе. После повторного чтения источника кэшированные результаты исключаются из повторного поиска, а найденные кандидаты заново проходят текущий matcher. Неоднозначные кандидаты остаются в очереди проверки; пользователь может заново искать любой трек.

Выбор пользователя для кандидата и исключение уже найденного трека сохраняются отдельно в локальном IndexedDB до 180 дней (максимум 25 000 решений). Ключ включает source provider, target provider и контекст каталога; Apple storefront и preview/account режимы не смешиваются. Для плейлистов включение хранится отдельно по ID плейлиста и позиции элемента, поэтому можно исключить одно вхождение, оставив тот же трек в других списках. Поиск и распространение выбранного результата группируют повторные source tracks по ISRC или стабильному provider ID. Для ISRC ключ дополнительно учитывает признаки версии (`live`, `remix`, `remaster` и другие): записи с одинаковым кодом, но конфликтующей версией, не наследуют чужое совпадение автоматически. Отдельные переключатели включения повторных вхождений остаются независимыми. При следующем поиске выбор восстанавливается только если сохранённый target track ID всё ещё присутствует среди актуальных кандидатов; иначе остаётся текущий результат matcher. Решения и результаты очищаются одной кнопкой. Сводка transfer job отдельно хранит в IndexedDB только пару сервисов, числа операций и короткий статус прогресса; план треков и данные сессий туда не попадают. Она нужна для ручной сверки после прерывания и не запускает повтор автоматически.

Эти пороги — консервативный старт, а не измеренная точность. Их нельзя считать доказанными для тысяч записей, каталогов всех четырёх сервисов, кавер-версий, одинаковых названий, фичерингов и региональных вариантов. Перед включением записи в аккаунт нужно собрать обезличенные labeled fixtures из пользовательских решений, измерить precision отдельно по языкам/версиям и настроить порог так, чтобы ошибочный перенос был редким. Неизвестные и неоднозначные записи должны оставаться в review queue.

## Массовая обработка

`demo/transfer-engine.js` содержит общий `searchMany(adapter, tracks)`: он объединяет одинаковые поисковые запросы и ограничивает параллелизм настройкой адаптера. Там же есть `discoverAllCollections()` и `readLibrary()`: engine проходит страницы обнаружения коллекций, затем читает каждую найденную favorites/playlist коллекцию до конца и собирает единый snapshot. `readCompleteCollection()` останавливается при повторе cursor, дедуплицирует favorites по provider ID, сохраняет повторные playlist items и позиции, сверяет `totalCount` и принимает checkpoint callback после каждой страницы. Без независимого total подтверждённость snapshot остаётся `false`. `transfer-core.createSnapshot()` поддерживает несколько коллекций одного аккаунта.

Массовый поиск выполняется с ограниченной параллельностью и объединяет дубликаты запроса. Когда первичная выдача не содержит безопасного автосовпадения, расширенный поиск по широкому и транслитерированному запросу повышает recall. В кэш записывается, закончился ли этот этап; неопределённые старые записи кэша повторно ищутся один раз после обновления алгоритма, подтверждённые выборы пользователя сохраняются. Если fallback временно недоступен, сохраняется первичная выдача, а неуспешное расширение можно повторить в следующем запуске. Для временных сетевых ошибок, HTTP 408, 429 и 5xx общий движок повторяет только catalog search до трёх раз с экспоненциальной паузой; 429 получает более длинный интервал и общий cooldown для оставшейся очереди этого запуска соблюдает `Retry-After`, чтобы другие workers не продолжали нагружать каталог. Отмена поиска прерывает ожидание и очередь. Точность, скорость, provider rate limits и поведение на тысячах записей ещё не измерены. Автоподбор остаётся консервативным: точный ISRC принимается только без явного конфликта версии записи, а metadata-only требует высокой confidence и отрыва от следующего кандидата; остальные случаи остаются в review queue. Для автоматического массового импорта нужна labeled-проверка качества на реальных наборах, прежде чем снижать пороги. Каждый adapter передаёт исходный provider ID, ISRC, нормализованные credits, версию, длительность, storefront и provenance, а также сохраняет порядок и повторы playlist items.

Чтобы массовый список не перегружал интерфейс, экран сверки показывает 50 строк за страницу и позволяет отфильтровать записи без уверенного совпадения. Поиск обновляет прогресс группами запросов, а не перестраивает весь DOM после каждого трека. Это снижает нагрузку от UI, но само по себе не доказывает, что целевые сервисы выдержат тысячи поисковых запросов: лимиты и скорость каждого каталога нужно измерить отдельно.

Apple Music account search выполняет точный lookup через `GET /v1/catalog/{storefront}/songs?filter[isrc]=...` и сохраняет catalog song IDs для последующей записи. Для массового поиска до 25 различных ISRC отправляются одним запросом; сейчас разрешены максимум два одновременных batch-запроса. 10 000 разных ISRC дают до 400 batch HTTP-вызовов, то есть примерно 200 волн до fallback и повторов; это оценка по параметрам адаптера, а не live-замер времени или лимитов. Если код не вернулся в ответе, поиск повторяется одиночно, затем используется fallback по названию и исполнителю. Apple документирует `filter[isrc]` и предупреждает, что один ISRC может вернуть несколько песен; matcher проверяет варианты и затем использует metadata confidence. Spotify search использует поле `isrc` в запросе Web API. ISRC-поиск Spotify описан в [официальной документации Search](https://developer.spotify.com/documentation/web-api/reference/search); Apple endpoint — [Get Multiple Catalog Songs by ISRC](https://developer.apple.com/documentation/applemusicapi/get-multiple-catalog-songs-by-isrc). Текущие страницы Apple Music и Spotify являются неофициальным транспортом активной пользовательской сессии, что отдельно ограничивает надёжность интеграции.

Spotify account search — отдельный запрос на каждый уникальный ISRC/metadata query; безопасного многотрекового `isrc` search в используемом Web API contract не подтверждено. Публичный Spotify Search принимает до 10 кандидатов на тип. Удалённый в феврале 2026 `GET /tracks?ids=...` был batch-fetch уже известных Spotify IDs, а не поиск по ISRC; его нельзя использовать для поиска целей, когда исходные ID принадлежат другому сервису. Для Яндекса и Звука bulk-search contract также не подтверждён. Поэтому приложение пока ограничивает параллельность двумя запросами на сервис, кэширует готовые результаты и не выдумывает групповой поиск. Источник cross-service catalog reference [streamnx](https://github.com/GeorgeGorbanev/streamnx) поддерживает Apple/Spotify/Yandex metadata и ISRC lookup лишь на части каталогов, но не account libraries, playlists или transfer; его license metadata на GitHub отсутствует.

## JSON-план

Каждая выбранная запись сохраняет provider ID, ISRC, название, исполнителей, альбом, длительность, исходный playlist ID и позицию. Блок `match` содержит метод, confidence и признак auto-match. Общая модель и builder плана находятся в `demo/transfer-core.js`: snapshot содержит несколько коллекций источника с отдельной полнотой, а план `music-transfer-plan` отдельно задаёт источник, назначение и нативную операцию `add_to_favorites` или `add_to_playlist`. Движок допускает любой из четырёх provider IDs как source/target; для каждого есть поиск и writer с fixture coverage, но live-трансфер не проверен.
