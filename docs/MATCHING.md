# Массовое сопоставление треков

Прототип содержит provider-neutral модуль `demo/matcher.js`. Он сравнивает нормализованные метаданные источника с результатами каталога назначения; текущий интерфейс использует только результаты Apple iTunes Search API.

## Порядок решения

1. Если ISRC есть на обеих сторонах и совпадает после нормализации, это точный кандидат.
2. Иначе считаются похожесть названия и исполнителя; альбом и длительность добавляют evidence, когда присутствуют с обеих сторон.
3. Маркеры версии записи (`live`, `remix`, `remaster`, `acoustic`, `radio edit`, `sped up`, и др.) предотвращают автоматическое принятие несовпадающих версий.
4. Метаданные автоматически выбираются только при score не ниже `0.96` и отрыве от следующего кандидата не меньше `0.035`; иначе запись направляется на ручную проверку.

Эти пороги — консервативный старт, а не измеренная точность. Их нельзя считать доказанными для тысяч записей, каталогов всех четырёх сервисов, кавер-версий, одинаковых названий, фичерингов и региональных вариантов. Перед включением записи в аккаунт нужно собрать обезличенные labeled fixtures из пользовательских решений, измерить precision отдельно по языкам/версиям и настроить порог так, чтобы ошибочный перенос был редким. Неизвестные и неоднозначные записи должны оставаться в review queue.

## Массовая обработка

`demo/transfer-engine.js` содержит общий `searchMany(adapter, tracks)`: он объединяет одинаковые поисковые запросы и ограничивает параллелизм настройкой адаптера (по умолчанию три). Текущий интерфейс вызывает его через Apple catalog adapter. Там же есть `discoverAllCollections()` и `readLibrary()`: engine проходит страницы обнаружения коллекций, затем читает каждую найденную favorites/playlist коллекцию до конца и собирает единый snapshot. `readCompleteCollection()` останавливается при повторе cursor, дедуплицирует favorites по provider ID, сохраняет повторные playlist items и позиции, сверяет `totalCount` и принимает checkpoint callback после каждой страницы. Без независимого total подтверждённость snapshot остаётся `false`. `transfer-core.createSnapshot()` поддерживает несколько коллекций одного аккаунта.

Это только общий orchestration layer; ни один реальный account adapter ещё не подключён к нему. Provider-level retry semantics, write idempotency, execution checkpoints и read-back для назначения всё ещё отсутствуют. Каждый адаптер должен передавать исходный provider ID, ISRC, нормализованные credits, версию, длительность, storefront и provenance, а также сохранять порядок и дубликаты playlist items.

## JSON-план

Каждая выбранная запись сохраняет provider ID, ISRC, название, исполнителей, альбом, длительность, исходный playlist ID и позицию. Блок `match` содержит метод, confidence и признак auto-match. Общая модель и builder плана находятся в `demo/transfer-core.js`: snapshot содержит несколько коллекций источника с отдельной полнотой, а план `music-transfer-plan` отдельно задаёт источник, назначение и нативную операцию `add_to_favorites` или `add_to_playlist`. Движок допускает любой из четырёх provider IDs как source/target и не ограничивает число записей; текущий UI пока реализует только поиск в Apple каталоге, поэтому верхний уровень честно помечен `preview-only` и `execution.writesPerformed` остаётся `0`.
