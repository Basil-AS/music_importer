# Локальный прототип переноса между сервисами

Целевая функция — перенос лайков и плейлистов в любом направлении между Spotify, Apple Music, Яндекс Музыкой и Звуком. В приложении собраны experimental source readers, catalog search adapters и target writers для всех четырёх сервисов. Все writers проходят fixtures, но ни один из 12 направленных маршрутов ещё не прошёл end-to-end live transfer; сквозной Chrome bridge сейчас также ждёт подключения расширения.

## Что можно попробовать

1. Открыть Web Player Spotify или сайт Звука и войти штатным способом.
2. Выбрать источник и передать библиотеку из локального расширения; также доступны демо-данные и CSV/JSON.
3. Выбрать каталог Apple или Яндекс Музыки и искать совпадения. Сопоставитель автоматически принимает только результат с высокой уверенностью; неоднозначные результаты остаются на ручную проверку.
4. При необходимости поправить запрос или версию, исключить запись либо выбрать совпадение вручную.
5. Скачать JSON-план `music-transfer-plan` с source/target provider IDs, исходными ID/ISRC/метаданными, target track IDs, методом и оценкой совпадения, playlist-порядком, полнотой и пропусками.

После поиска список разбивается на страницы по 50 треков; фильтр оставляет записи без уверенного совпадения и ошибки поиска. Уверенные автоматические совпадения остаются включёнными, а тысячи строк не строятся в DOM одновременно.

## Данные и границы

- CSV и JSON читаются браузером и не отправляются на сервер проекта.
- Передача из Chrome connector доступна с локальных адресов `127.0.0.1:8000/8001` и `localhost:8000/8001`; service worker передаёт только полностью подтверждённый snapshot, без cookies и токенов. Подготовлен GitHub Pages deployment на release-ветку `master`, но сам Pages ещё не включён и URL не опубликован.
- Страница проверяет наличие локального расширения на старте; при отсутствии ответа объясняет, как обновить extension и проверить доступ к local origin, и оставляет кнопку повтора.
- Сразу после подключения расширения приложение автоматически запускает readers для открытых вкладок Spotify, Яндекс Музыки и Apple Music и автосканер Звука, собирает подтверждённые snapshots и показывает число лайков/плейлистов в карточках источников. Пользователь выбирает источник после сбора. Сканер Звука последовательно меняет URL открытой вкладки сервиса; её нужно оставить открытой. Для сессии, открытой позже, доступно повторное сканирование.
- Для preview-списков поиск Apple обращается к публичному iTunes Search API. Для подтверждённой аккаунтной библиотеки поиск Apple идёт через Apple Music catalog API из открытой авторизованной вкладки, чтобы целевые ID были catalog IDs. Яндекс поиск и transfer также используют открытую вкладку. Секретные заголовки остаются внутри provider page closure и не попадают в приложение или extension storage.
- Первичный порог авто-подбора консервативный и пока не откалиброван на реальных библиотеках: exact ISRC принимается автоматически; по метаданным — только при уверенно высоком score и заметном отрыве от второго кандидата. Совпадение версий (live/remix/remaster и др.) проверяется отдельно. Полные результаты каталога и решения пользователя кэшируются локально, поэтому после нового чтения аккаунта восстанавливаются кандидаты и прежний выбор, если target ID ещё найден. Массовый перенос тысяч записей ещё не подтверждён. Во время записи IndexedDB хранит только краткую job-сводку и прогресс, без credentials и плана треков; автоматического продолжения нет. После прерывания пользователь должен сверить цель вручную, прежде чем начать новый перенос.
- Matcher, `demo/transfer-core.js` и `demo/transfer-engine.js` отделяют модель данных, план и orchestration от сервисов: общий поиск объединяет повторы и ограничивает конкуренцию, общий reader проходит cursor-страницы и сохраняет playlist positions. Модель допускает любой из четырёх сервисов как источник/назначение; target adapters подключаются поэтапно.
- Общий executor задаёт целевой поток: требует подтверждённой полноты снимка, явного согласия и read-back. Yandex writer проверяет существующие likes, добавляет недостающие, создаёт приватные плейлисты, вставляет треки партиями с актуальной revision и сравнивает ID/order после записи. UI предупреждает при попытке закрыть страницу во время живой записи и сохраняет локальную сводку job/progress. Автоматического возобновления нет: после частичной ошибки или прерывания новый перенос заблокирован до ручной сверки цели, поскольку повтор может создать дубликат плейлиста.
- План представляет mixed-перенос всей библиотеки: favorites идут отдельными `add_to_favorites`, playlist items — в соответствующие target playlists. Apple, Yandex, Zvuk и Spotify writers сверяют лайки, ID и порядок обратным чтением; все требуют полной исходной библиотеки и явного подтверждения, live-write evidence пока нет.
- Apple Music source reader использует `inFavorites`, сохраняет повторы/порядок плейлистов и останавливается при неподтверждённой полноте. Apple target writer использует официальный REST API из first-party page session, fixture-tested; live scan, CORS/auth setup и write propagation ещё не проверены. См. [`APPLE_TRANSFER.md`](APPLE_TRANSFER.md).
- Для Яндекса read route shapes и CORS подтверждены из авторизованной страницы и публичного terminal path; full extension scan и write/read-back пока fixture-only. Локальный Zvuk target writer использует GraphQL operations из community client, но deployed mutation contract и live write ещё не подтверждены. Spotify target writer добавлен на основе частных Web Player API: поиск, лайки, создание плейлистов, root-list insert и read-back покрыты fixtures, live API не запускали. См. [`SPOTIFY_TRANSFER.md`](SPOTIFY_TRANSFER.md).

## Запуск

Из корня проекта:

```bash
python3 -m http.server 8000 --bind 127.0.0.1 --directory demo
```

Открыть <http://127.0.0.1:8000>. Для сетевого поиска нужен локальный HTTP-сервер: при открытии `index.html` как `file://` браузер может заблокировать запрос к каталогу.

Для прямой передачи библиотеки из расширения откройте одну из поддержанных локальных страниц (`127.0.0.1:8000/8001` или `localhost:8000/8001`) и перезагрузите её после установки/обновления расширения. Сервер раздаёт файлы из текущего checkout. Если переключить checkout на ветку, где нет `demo/`, уже запущенный сервер продолжит слушать порт, но будет возвращать `404`. Для параллельной работы с исследовательской веткой используйте отдельный worktree для `feature/interactive-importer-mvp` и запускайте команду из него.

## Ручная проверка

В браузере проверены preview-поиск для 6 демо-треков, формирование и скачивание provider-neutral JSON-плана; preview не пишет в аккаунт. Дополнительно загружен JSON fixture в формате Zvuk playlist export: оба трека распознаны, порядок/тип коллекции показаны, ошибок консоли нет. Provider source/target commands проходят изолированные fixtures. Новый all-accounts coordinator проверен на старте четырёх readers и агрегировании готовых snapshots.

Диагностика подключения 2026-10-28: локальный сервер `127.0.0.1:8001` отвечает `200 OK` и раздаёт `music_importer-mvp/demo`. В пользовательском Chrome ping не получил `extension-ready`; после перезагрузки страницы результат тот же. В консоли страницы нет ошибок JavaScript. Следовательно, локальное расширение не внедрилось в страницу MVP или не ответило на ping. Возможные причины — расширение не установлено/выключено, загружена старая копия или Chrome не дал ему доступ к `http://127.0.0.1:8001`. Сам вход в Apple Music это соединение не устанавливает. В этой сессии экран показывал шесть демо-треков, а поиск по каталогу Apple нашёл 6/6 из кэша; это проверяет только интерфейс и публичный каталог, не чтение лайков из Apple Music или Звука. Все четыре страницы сервисов открыты в Chrome, но сканирование библиотек и запись в аккаунты не запускались, так как extension bridge не подключён. В интерфейс добавлена инструкция: загрузить/перезагрузить unpacked extension из `chrome-extension/` текущего MVP checkout через `chrome://extensions`, разрешить сайту доступ к локальному адресу и четырём доменам сервисов, обновить их вкладки и повторить проверку.

## Текущая проверка авто-подбора (2026-10-28)

Свежая браузерная сессия загрузила все 6 демо-записей, получила результаты Apple для 6/6 и завершилась без ошибок в консоли. После уточнения поискового запроса по альбому 4 записи авто-выбраны как уникальные metadata matches на 98%; две остались на ручную проверку из-за отсутствия альбома и неоднозначной выдачи. Это подтверждает работу UI-пути и осознанный review fallback на маленьком демонстрационном списке, но не измеряет точность на реальной библиотеке и не доказывает масштаб на тысячах. Поиск демо выполняется через публичный preview endpoint; он не проверяет связь с Apple Music account session и не пишет в аккаунт.

Дополнительная runtime-проверка IndexedDB в пользовательском Chrome: выбор альтернативного кандидата и снятый с него флажок сохранились после перезагрузки, а поиск восстановился из локального кэша. Явное исключение трека также пережило перезагрузку и не попало в счётчик очереди проверки; после проверки выбор восстановлен на вариант каталога. Это проверяет только demo-список и Apple preview UI, не чтение сессии аккаунта и не live-запись.

Журнал job переноса не разрешает отправить write-команду, пока не сохранён начальный checkpoint в IndexedDB. После ответа сервиса успешная запись помечается complete; частичная ошибка или потеря связи блокирует следующий перенос, пока пользователь не подтвердит сверку целевого аккаунта. При недоступном IndexedDB live-write блокируется. План и данные сессии в журнал не попадают.

Смешанный core сценарий отдельно прогнан через mock destination adapter: один `add_to_favorites`, один `add_to_playlist`, пустой плейлист сохранён, read-back завершился `complete`. Extension→app handoff проверяется отдельно после установки обновлённого unpacked extension.

## Статус охвата

Все 12 source/target combinations теперь подключены на уровне readers, search adapters и writers, но ни одно из 12 направлений не прошло live end-to-end проверку. Четыре target adapters имеют fixture coverage, но не live-verified.

Общий catalog search повторяет временные сетевые ошибки, HTTP 408, 429 и 5xx максимум три раза с backoff; постоянные 4xx не повторяются, отмена прерывает ожидание. Поиск по умолчанию включает альбом и при нулевой выдаче повторяет запрос только с названием и исполнителем; отредактированный пользователем запрос выполняется без fallback. Apple группирует до 25 ISRC в один catalog query и добирает отсутствующие результаты индивидуальными запросами. Полный Node fixture suite: 76/76 passed (2026-10-28), включая проверку журнала переноса при потере IndexedDB и сверке незавершённой записи. Source/catalog/write fixtures есть для всех четырёх сервисов; для Звука дополнительно проверен worker state machine от сбора лайков до подтверждённого snapshot со списком, содержимым и пустым плейлистом. Эти fixtures моделируют сервисные ответы и Chrome tabs/storage, но не используют живые пользовательские сессии. Для всех 12 направлений отдельно выполнена in-memory симуляция общего transfer engine: подтверждённые лайки и плейлисты записаны, пустой плейлист сохранён, read-back подтвердил результат. Эти сценарии проверяют общий orchestration/core, не живые API провайдеров; они не заменяют route end-to-end live-проверку и не доказывают пропускную способность для тысяч треков. GitHub Actions запускает syntax, manifest и fixture проверки для PR в `develop`.

Подробности Yandex reader и неопровергнутые runtime/CORS ограничения: [`YANDEX_CONNECTOR.md`](YANDEX_CONNECTOR.md).
