# Локальный прототип переноса между сервисами

Целевая функция — перенос лайков и плейлистов в любом направлении между Spotify, Apple Music, Яндекс Музыкой и Звуком. Локальные readers есть для Звука, Spotify и Яндекс Музыки; Apple Music reader добавлен, fixture-tested и ждёт live-проверки в установленном расширении. Яндекс Музыка сейчас единственная экспериментальная цель с записью и read-back. Ни один из 12 направленных маршрутов ещё не прошёл end-to-end live transfer.

## Что можно попробовать

1. Открыть Web Player Spotify или сайт Звука и войти штатным способом.
2. Выбрать источник и передать библиотеку из локального расширения; также доступны демо-данные и CSV/JSON.
3. Выбрать каталог Apple или Яндекс Музыки и искать совпадения. Сопоставитель автоматически принимает только результат с высокой уверенностью; неоднозначные результаты остаются на ручную проверку.
4. При необходимости поправить запрос или версию, исключить запись либо выбрать совпадение вручную.
5. Скачать JSON-план `music-transfer-plan` с source/target provider IDs, исходными ID/ISRC/метаданными, target track IDs, методом и оценкой совпадения, playlist-порядком, полнотой и пропусками.

## Данные и границы

- CSV и JSON читаются браузером и не отправляются на сервер проекта.
- Передача из Chrome connector доступна с локальных адресов `127.0.0.1:8000/8001` и `localhost:8000/8001`; service worker передаёт только полностью подтверждённый snapshot, без cookies и токенов.
- Поиск Apple обращается к публичному Apple iTunes Search API; Apple получает введённые названия и исполнителей. Для Яндекс Музыки запрос идёт через открытую вкладку с активной сессией; cookies/tokens не копируются в приложение или extension storage.
- Первичный порог авто-подбора консервативный и пока не откалиброван на реальных библиотеках: exact ISRC принимается автоматически; по метаданным — только при уверенно высоком score и заметном отрыве от второго кандидата. Совпадение версий (live/remix/remaster и др.) проверяется отдельно. Массовый перенос тысяч записей ещё не подтверждён.
- Matcher, `demo/transfer-core.js` и `demo/transfer-engine.js` отделяют модель данных, план и orchestration от сервисов: общий поиск объединяет повторы и ограничивает конкуренцию, общий reader проходит cursor-страницы и сохраняет playlist positions. Модель допускает любой из четырёх сервисов как источник/назначение; target adapters подключаются поэтапно.
- Общий executor задаёт целевой поток: требует подтверждённой полноты снимка, явного согласия и read-back. Yandex writer проверяет существующие likes, добавляет недостающие, создаёт приватные плейлисты, вставляет треки партиями с актуальной revision и сравнивает ID/order после записи. Повторный запуск после частичной ошибки может создать дубликат плейлиста; проверяйте целевой аккаунт перед повтором.
- План представляет mixed-перенос всей библиотеки: likes идут отдельными `add_to_favorites`, playlist items — в соответствующие target playlists; общий executor требует подтверждённую полноту снимка, отдельное согласие и read-back. Реальная запись экспериментально подключена только для Яндекс Музыки.
- При цели Apple Music план по-прежнему `preview-only`; Apple target write не подключён. Для цели Яндекс Музыка отдельное подтверждение запускает экспериментальную запись только для полного снимка из account connector.
- Spotify, Яндекс и Apple Music имеют experimental source connectors из активных вкладок. Apple reader использует `inFavorites`, сохраняет повторы/порядок плейлистов и останавливается при неподтверждённой полноте; live scan требует перезагрузить локальное расширение. Для Яндекса из авторизованной страницы и публичного terminal запроса подтверждены API response shapes и CORS для основного read path/metadata hydration; extension bridge и full-library completeness всё ещё требуют проверки установленным расширением. Yandex target writer собран по частному/community API-контракту и проверен только моками.
- Локальный Zvuk connector собирает лайки и плейлисты и сверяет totals. Apple, Spotify и Zvuk destination writers остаются впереди.

## Запуск

Из корня проекта:

```bash
python3 -m http.server 8000 --bind 127.0.0.1 --directory demo
```

Открыть <http://127.0.0.1:8000>. Для сетевого поиска нужен локальный HTTP-сервер: при открытии `index.html` как `file://` браузер может заблокировать запрос к каталогу.

Для прямой передачи библиотеки из расширения откройте одну из поддержанных локальных страниц (`127.0.0.1:8000/8001` или `localhost:8000/8001`) и перезагрузите её после установки/обновления расширения. Сервер раздаёт файлы из текущего checkout. Если переключить checkout на ветку, где нет `demo/`, уже запущенный сервер продолжит слушать порт, но будет возвращать `404`. Для параллельной работы с исследовательской веткой используйте отдельный worktree для `feature/interactive-importer-mvp` и запускайте команду из него.

## Ручная проверка

В браузере проверены поиск для 6 демо-треков, формирование и скачивание provider-neutral JSON-плана: `type=music-transfer-plan`, source `zvuk`, target `apple-music`, три операции и три записи review/skip, `execution.writesPerformed=0`. Дополнительно загружен JSON fixture в формате Zvuk playlist export: оба трека распознаны, порядок/тип коллекции показаны, ошибок консоли нет. Локальный extension→app handoff добавлен, но ещё не проверен с установленным расширением. Это не подтверждает provider login, live Zvuk capture, Apple account write или полноту больших библиотек.

## Текущая проверка авто-подбора (2026-10-28)

Свежая браузерная сессия загрузила все 6 демо-записей, получила результаты Apple для 6/6 и завершилась без ошибок в консоли. Две записи были авто-выбраны как уникальные metadata matches на 98%; четыре остались на ручную проверку из-за неоднозначности. Это подтверждает работу UI-пути и осознанный review fallback на маленьком демонстрационном списке, но не измеряет точность на реальной библиотеке и не доказывает масштаб на тысячах.

Смешанный core сценарий отдельно прогнан через mock destination adapter: один `add_to_favorites`, один `add_to_playlist`, пустой плейлист сохранён, read-back завершился `complete`. Extension→app handoff проверяется отдельно после установки обновлённого unpacked extension.

## Статус охвата

Проект не поддерживает заявленный полный охват: все 12 directed pairs не реализованы и live transfer ещё не прошёл проверку на аккаунте. Один экспериментальный target adapter (Яндекс) имеет fixture coverage, но не live-verified.
