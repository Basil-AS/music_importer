# Направление продукта

Подробная сравнительная схема пользовательского входа, токенов и зависимости от developer credentials: [AUTHENTICATION.md](AUTHENTICATION.md).
Модель локального расширения, которое отдаёт только список треков, описана в [LOGIN_MECHANISMS.md](LOGIN_MECHANISMS.md).

## Целевой опыт

Человек открывает сервис, выбирает откуда и куда перенести музыку, входит в свои аккаунты и запускает перенос. Главный первый сценарий — перенести лайкнутые треки из Spotify, Яндекс Музыки и Звука в Apple Music **Favorite Songs**. Сервис показывает найденные совпадения и спорные случаи до записи, не вводит собственного лимита на количество треков и даёт повторить/продолжить перенос после сбоя.

Под «без привязки к автору» понимается, что запуск не должен требовать OAuth client ID, developer account, серверного секрета или платной подписки, принадлежащих создателю Music Importer. Пользовательские cookies, OAuth-токены и музыкальные данные не должны проходить через сервер проекта, если задачу можно выполнить локально.

## Продуктовые требования

- **Минимум действий:** подключить источники и Apple Music, просмотреть сводку, подтвердить перенос.
- **Своя авторизация:** вход ведёт на домен провайдера; сервис не просит пароль/2FA и не пересылает их себе.
- **Простой вход без аккаунта разработчика:** для пользователя подключение должно выглядеть как «Войти в Spotify/Яндекс/Звук/Apple». Внутри этого всё равно нужен поддерживаемый провайдером механизм: OAuth требует client ID приложения, а веб-сессия требует открыть сам сайт и бережно использовать локальную сессию. Прямой ввод пароля в импортёр не является способом авторизации.
- **Локальная обработка:** токены хранятся только на устройстве пользователя в системном хранилище секретов; библиотека обрабатывается локально и удаляется после завершения по выбору пользователя.
- **Без авторской инфраструктуры:** не полагаться на личные OAuth-приложения, developer credentials или облачный backend Basil-AS/Codex. Если провайдер этого требует, считать интеграцию пока не соответствующей цели и явно показывать зависимость.
- **Лайки прежде плейлистов:** писать именно в Apple Favorite Songs, а не только создавать плейлист или добавлять записи в общую Library.
- **Без скрытых лимитов:** проходить страницы и безопасно продолжать работу; ограничения самого провайдера раскрывать до начала переноса.
- **Проверяемость:** сопоставить число исходных лайков, найденных кандидатов, записей и read-back; повторы не должны добавлять дубликаты.

## Архитектурный вывод на текущем этапе

Основной кандидат — **локально запускаемый клиент**, а не единый hosted importer: это позволяет каждому пользователю проходить вход у провайдера на своём устройстве и не передавать его библиотеку серверу проекта. Интеграции должны иметь явный статус: официальный OAuth, пользовательская сессия/private API, файл экспорта или native local app. Не скрывать переход между этими способами.

Строгая цель «одна кнопка, все аккаунты, без credentials автора» пока не доказана. Самые важные проверки — подтвердить бесплатный локальный write в Apple Favorite Songs, полноту лайков Звука и подобрать для Яндекса вход с минимальными scopes; проверенный Android Device Flow consent оказался слишком широким. Для Spotify нужно выбрать честный путь между ручным архивом и неофициальным Web Player API. Если единственный путь требует shared app credentials разработчика или несоразмерные permissions, это считается архитектурным несоответствием цели, а не незаметной предпосылкой реализации.

Не хранить там пользовательские токены или музыкальные данные; GitHub отдельно ограничивает использование Pages как бесплатного хостинга SaaS. |

Это отдельная local sign-in модель, не копирование Chrome session. | Самый гибкий контейнер и удобный вариант для интеграции с Music.app; потребует собрать/публиковать бинарники под ОС и объяснить системные предупреждения/подпись. `sizwinz/SoundShift` показывает такой UX для Spotify/YT Music, но с private API и без Apple/Yandex/Zvuk. **Self-hosted Docker UI — ещё один сильный UX reference:** готовый интерфейс запускается как локальная web app и может быть проще в ежедневном использовании, чем отдельная страница расширения. Текущие кандидаты требуют ручного переноса чувствительных session tokens и не содержат обоих российских source adapters; поэтому в нашем проекте такую панель следует связать с локальным browser connector, а не просить скопировать cookies/tokens.

**Рекомендация для первого выпуска: GitHub Pages — витрина и загрузка, перенос — локальное приложение.** Pages даёт одну ссылку на красивый сайт с инструкциями, совместимостью и кнопкой загрузки. Сам перенос должен выполняться локально: hosted Pages не может читать уже открытые вкладки/сессии как расширение, а GitHub прямо запрещает использовать Pages как бесплатный SaaS-хостинг. Поэтому не размещать на Pages рабочий transfer dashboard, сбор пользовательских библиотек или вход/токены.

Для функционального прототипа в первую очередь делаем полноэкранную Chrome/Chromium extension dashboard: она устанавливается отдельно, получает доступ только после явного действия пользователя и выполняет provider connector на устройстве. Chrome `activeTab` даёт временный доступ к текущей вкладке по клику; публикация в Chrome Web Store требует одноразовой регистрации разработчика, а бесплатная установка из GitHub Releases требует ручного `Load unpacked` и Developer mode. Если ручная установка окажется слишком сложной для целевых пользователей, следующий вариант — собрать локальный desktop app с той же панелью и отдельной авторизацией у провайдеров. Это требует отдельных бинарных сборок и не использует существующую Chrome-сессию.

Итого: красивую Pages-витрину можно сделать быстро, но одна ссылка на Pages не даст «вошёл в аккаунты и перенёс лайки». Самый дешёвый работающий MVP — Pages + локально установленное расширение; для широкой аудитории отдельно сравнить стоимость и шаги Chrome Web Store с установкой desktop builds. Ссылки: [назначение и ограничения GitHub Pages](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#pages), [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [регистрация Chrome Web Store](https://developer.chrome.com/docs/webstore/register/), [установка unpacked extension](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load-unpacked).

Для первого внешнего прототипа проще всего отдать extension архивом через GitHub Releases и показать установку из Developer mode. Это бесплатно, но установка не в один клик. Если решим, что «установить за одну кнопку» важнее нулевой платы владельца проекта, Chrome Web Store даст обычный магазинный install flow; Google требует одноразовую регистрацию **от издателя**, пользователь за расширение не платит. В расширении надо запрашивать только нужный доступ: `activeTab` даёт временный доступ к текущей вкладке после нажатия пользователем, но API-хосты вне её origin потребуют отдельных явно объяснённых host permissions. Ссылки: [Chrome activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [регистрация издателя Chrome Web Store](https://developer.chrome.com/docs/webstore/register/).

Официальный Apple Music API действительно предоставляет `POST /v1/me/favorites`, который добавляет песню в Favorite Songs, но REST-вызов требует developer token и авторизацию пользователя. Поэтому destination adapter нужно отдельно подтвердить через локальный Music.app/AppleScript или MusicKit, прежде чем обещать полностью бесплатный перенос без авторских credentials. См. [Apple Add resource to favorites](https://developer.apple.com/documentation/applemusicapi/add-resource-to-favorites?changes=la) и [MusicKit user authentication](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit).

После POC оставляем Tauri как путь для пользователей без Chrome/Chromium и для более цельного desktop UX; сейчас не делаем его условием первого запуска, потому что он добавляет сборки, подпись и отдельные provider WebView login flows. Если приоритет сместится к установщику вместо расширения, этот выбор можно переоценить по результатам auth и Apple Favorites POC.

Свежий reference [Skalas/music-sync](https://github.com/Skalas/music-sync/tree/9f961d9e439885eaff6dff6da125e238f278da6e) показывает альтернативную локальную панель FastAPI + TypeScript и конкретный Apple `favorited` путь через Music.app. Он не меняет выбор первого прототипа: проект требует `uv`/`npm`, пользовательский Spotify OAuth app и вручную созданный Shortcut, не поддерживает Яндекс/Звук, а его GitHub-репозиторий не объявляет лицензию. Берём его как source/UI reference, не как готовую базу.

### Решение для запуска и первого UX-прототипа

**GitHub Pages — общая красивая точка входа; подключение аккаунтов и перенос выполняются локально.** Pages публикует HTML/CSS/JS, поэтому на ней можно сделать адаптивный лендинг, демо интерфейса, статус совместимости, инструкции и каталог релизов. Сама страница не получает права читать авторизованные вкладки Chrome; запросы к чужим API дополнительно зависят от CORS. Не просим пользователей вводить пароль, вставлять токены или отдавать библиотеку на Pages.

Требование «быстро запустить кому угодно» раскладываем на два понятных шага: человек сначала открывает одну ссылку, затем запускает локальный клиент, которому можно доверить работу с его аккаунтами. На стартовой странице будет одна заметная кнопка «Начать» и автоматический выбор инструкции/сборки под платформу. Красивое управление — полноэкранная dashboard-страница локального клиента с подключениями, прогрессом, preview совпадений, подтверждением записи и отчётом. Pages остаётся доступной без установки и показывает демо/справку, но не притворяется готовым importer.

**Первый технический прототип — локальная dashboard-панель с provider-specific login adapters.** Для Звука сначала проверим найденный QR/device flow с хранением token в системном secret store; для сервисов, где пользователь уже вошёл в Chrome, расширение-коннектор может читать только выбранный provider и передавать локальному клиенту нормализованный список треков. Это позволяет не сводить все входы к сбору cookies и не просит пользователя копировать токен. Spotify официально всё ещё требует зарегистрированный app Client ID; для браузеров без Chrome позже понадобятся desktop-сборки с самостоятельным входом там, где провайдер разрешает такой flow. Подписанные сборки и поддержка отдельных платформ потребуют отдельной работы.

Бесплатный первый запуск распространяем через GitHub Releases: расширение вручную загружается через Developer mode, локальная панель — из релиза. Это честная цена за отсутствие платы за магазин и авторских SaaS credentials. Chrome Web Store может упростить установку позже, но публикация требует разовой регистрации разработчика. Не называем распакованную установку «установкой в один клик».

Dashboard главная и отдельная, открывается в новой вкладке/окне, не в маленьком popup. Первый экран строится вокруг понятного процесса:

1. Карточки источников и Apple Music показывают «не подключён», «готов» или понятную причину ошибки; подключение всегда инициируется пользователем.
2. Кнопка «Проверить лайки» открывает нужный сервис или использует явно выбранную активную вкладку; показываются прогресс, количество страниц и итоговое число найденных лайков.
3. До любых изменений видны счётчики совпадений, неоднозначных треков и пропусков; пользователь может исправить спорные соответствия.
4. Отдельное подтверждение запускает запись в Apple Favorite Songs; после неё показываются результат и read-back-проверка. Повторный запуск продолжает безопасно и не создаёт дубликаты.
5. Страница состояния объясняет, какие данные обрабатываются локально, какие разрешения нужны, как отключить сервис и очистить локальные данные.

**Практическая цена бесплатного запуска:** исходники и ZIP можно раздавать через GitHub Releases, но установка непубликованного Chrome extension требует ручной загрузки распакованной папки в Developer mode. Поэтому это прототип коннектора для проверки входа через уже открытую Chrome-сессию, не финальное обещание «установка в один клик». Для широкого запуска сравнить подписанные desktop-сборки с публикацией расширения в магазине; Firefox/Safari потребуют отдельной проверки.

Pages не должен содержать tracker, токены, музыкальные списки или авторские секреты. Расширение также запрашивает только необходимые host permissions и выполняет чтение после действия пользователя; не извлекает cookies и не сохраняет общий bearer, если тот же результат можно получить через текущую вкладку и передать в локальную очередь только как нормализованные метаданные.

Репозиторий [SpotiCloud Sync](https://github.com/artart222/spoticloud/tree/e5d6018b4dabae05171abc807beac3f11e2c8535) — практический proof-of-concept локального Chrome extension без API keys/backend, с экспортом JSON и управлением длинной задачей. Его маленький popup, DOM-only export без полноты/total reconciliation и отсутствие Apple/Yandex/Zvuk показывают, что заимствовать стоит локальные permissions и паузу/возобновление, но UI мигратора должен быть отдельной полноэкранной панелью, а экспорт — API/страничный connector с проверкой полноты.

[SoundShift](https://github.com/sizwinz/SoundShift/tree/0a468fbe24616a0e48a53c6fe147df841bf0380c) даёт второй проверяемый архитектурный reference: вместо подключения к существующему Chrome он открывает отдельную auth WebView и сохраняет credentials локально; его полноэкранная панель удобна для сложного match review. Пока не выбираем его как готовую основу: проект закрывает только Spotify/YT Music, а auth использует private web-player contracts. Этот подход оставляем кандидатом на desktop-вариант после минимальных POC для Звука, Яндекса и Apple Favorites.

[`zvuk/kithara`](https://github.com/zvuk/kithara/tree/1e49fd342bcb614dba31db8c8a6d675b9dbeaf42) открывает ещё один путь для запуска: локальный клиент начинает QR/device login, пользователь подтверждает его на домене Звука, а token остаётся в системном secret store. Это пока статический source audit; Kithara сам не делает полный liked export. Использовать как контракт-кандидат и проверить live до реализации.

`RoninHikami/Crossfade` — полезный интерфейсный reference для выбора источника/цели, прогресса, паузы/повтора и истории; он уже соединяет Яндекс/Spotify/Звук/YouTube Music локальным extension. Но Apple target отсутствует, Spotify требует app ID/allowlist, Zvuk любит через непагинированный `userTracks`, лицензия не объявлена. Использовать его как исследование UX и endpoint patterns, не как основу кода.


Pages не должен содержать tracker, токены, музыкальные списки или авторские секреты. Локальный клиент хранит данные на устройстве; connector запрашивает только необходимые разрешения и выполняет чтение после действия пользователя. Не извлекает cookies и не сохраняет общий bearer, если тот же результат можно получить из контекста пользовательской вкладки, передав локальному клиенту только нормализованные метаданные.

Это даёт понятный бесплатный старт и красивую панель, сохраняя локальные аккаунты и данные. Для человека без Chrome нужен desktop-вариант; для Apple Music в браузере может понадобиться developer token. Apple подтверждает, что MusicKit Web автоматически ведёт Music User Token для запросов пользователя, но API также требует developer token; это остаётся открытым препятствием для простого входа без credentials автора. Выбор production packaging сделаем после POC записи Favorite Songs через Music.app и проверки connector-а на полноту чтения лайков.

Технические основания: [GitHub Pages — что это](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [ограничения Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [разрешения расширений Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), [регистрация Chrome Web Store разработчика](https://developer.chrome.com/docs/webstore/register/), [установка распакованного расширения](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load-unpacked), [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Apple MusicKit user auth](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit), [Apple developer tokens](https://developer.apple.com/documentation/AppleMusicAPI/generating-developer-tokens).

## Ближайшая последовательность

1. Зафиксировать минимальные пользовательские данные каждого источника и API/auth route в provider inventory.
2. Проверить локальный Apple Music.app Favorite Songs write/read-back на одной явно выбранной тестовой записи.
3. Повторно проверить полноту курсорного экспорта Звука и найти least-privilege авторизацию Яндекс Музыки; не использовать широкий Android client consent как готовый путь.
4. Сравнить для Spotify API PKCE, Account Data archive и Web Player session по UX, устойчивости, правилам и зависимости от app owner.
5. После этого собрать POC связки Pages → локальный dashboard → Chrome connector и оценить шаги установки; затем выбрать desktop/store packaging по фактическому числу кликов и поддерживаемым платформам.
