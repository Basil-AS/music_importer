# Направление продукта

Подробная сравнительная схема пользовательского входа, токенов и зависимости от developer credentials: [AUTHENTICATION.md](AUTHENTICATION.md).
Модель локального расширения, которое отдаёт только список треков, описана в [LOGIN_MECHANISMS.md](LOGIN_MECHANISMS.md).

## Целевой опыт

Человек открывает сервис, выбирает откуда и куда перенести музыку, входит в свои аккаунты и запускает перенос. Главный первый сценарий — перенести лайкнутые треки из Spotify, Яндекс Музыки и Звука в Apple Music **Favorite Songs**. Сервис показывает найденные совпадения и спорные случаи до записи, не вводит собственного лимита на количество треков и даёт повторить/продолжить перенос после сбоя.

Под «без привязки к автору» понимается, что запуск не должен требовать OAuth client ID, developer account, серверного секрета или платной подписки, принадлежащих создателю Music Importer. Пользовательские cookies, OAuth-токены и музыкальные данные не должны проходить через сервер проекта, если задачу можно выполнить локально.

## Продуктовые требования

- **Минимум действий:** подключить источники и Apple Music, просмотреть сводку, подтвердить перенос.
- **Своя авторизация:** вход ведёт на домен провайдера; сервис не просит пароль/2FA и не пересылает их себе.
- **Простой вход без аккаунта разработчика:** для пользователя подключение должно выглядеть как «Войти в Spotify/Яндекс/Звук/Apple». Внутри этого всё равно нужен поддерживаемый провайдером механизм: OAuth требует client ID приложения, а веб-сессия требует открыть сам сайт и бережно использовать локальную сессию. Прямой ввод пароля в импортёр не является способом авторизации.
- **Локальная обработка:** токены хранятся только на устройстве пользователя в системном хранилище секретов; библиотека обрабатывается локально и удаляется после завершения по выбору пользователя.
- **Без авторской инфраструктуры:** не полагаться на личные OAuth-приложения, developer credentials или облачный backend Basil-AS/Codex. Если провайдер этого требует, считать интеграцию пока не соответствующей цели и явно показывать зависимость.
- **Лайки прежде плейлистов:** писать именно в Apple Favorite Songs, а не только создавать плейлист или добавлять записи в общую Library.
- **Без скрытых лимитов:** проходить страницы и безопасно продолжать работу; ограничения самого провайдера раскрывать до начала переноса.
- **Проверяемость:** сопоставить число исходных лайков, найденных кандидатов, записей и read-back; повторы не должны добавлять дубликаты.

## Реальные ограничения провайдеров

| Провайдер | Удобный вход | Зависимость от приложения автора | Что ближе к целевому UX |
|---|---|---|---|
| Spotify | Официальный Web API поддерживает OAuth PKCE, но новые Development Mode apps требуют активный Premium у app owner и ограничивают пользователей. Проверен open-source `sp_dc` + TOTP путь получения user-bound Web Player bearer без app ID; отдельный Saved Tracks вызов с новым bearer ответил `429`, поэтому доступ к лайкам этим способом ещё не доказан. | Для официального пути — да: один client ID на разработчика и Premium у владельца. Browser session избегает app ID, но зависит от private API и меняющегося контракта. | Локальный отдельный browser profile — доказанный open-source UX reference, не готовая Apple-интеграция. Архивный `YourLibrary.json` — более переносимый ручной fallback; private Web Player API требует планирования на поломки. |
| Яндекс Музыка | Cookie-session read path уже дал `200`; `jrfrigat/YandexMusic` добавляет best-effort Passport QR sign-in и OAuth token exchange. | Cookie read не требует app ID; Device Flow требует client credentials, а QR flow использует shared Music client ID + implicit token и undocumented Passport contract. | Local QR UX потенциально короче ручного token/cookie ввода, но остаётся проверить consent scopes и live flow; fallback — активная browser session с read-only API. |
| Звук | После входа на домене Звука профильный `GET /api/tiny/profile` или `/api/v2/tiny/profile` возвращает session token; Chrome live дал `200` для обоих. | Публичная developer console не найдена; private GraphQL/Tiny API, WAF и отзывной session token. Без cookies чистый CLI получил `418`. | Ближе к UX кнопки «Войти в Звук» через локальную browser session; пароль/OTP остаются у провайдера, token использовать только локально. Требуются cursor reconciliation и проверка подписочных прав; refresh contract не найден. |
| Apple Music | MusicKit / REST API требует Apple developer token; Favorites REST write требует также пользовательскую авторизацию. | Да для REST API: developer token выпускается через developer credentials. | Проверить macOS Music.app как локальный write path в Favorite Songs; встроенный Apple Transfer — готовый кандидат, но список источников зависит от аккаунта/региона и работает как отдельная функция Apple. |

Источники этих ограничений и подробные статусы проверок: [Spotify](providers/spotify.md), [Spotify OpenAPI inventory](providers/spotify-openapi-inventory.md), [Apple Music](providers/apple-music.md), [Яндекс Музыка](providers/yandex-music.md), [Звук](providers/zvuk.md), [Zvuk API inventory](providers/zvuk-api-inventory.md), [API matrix](API_MATRIX.md).

## Архитектурный вывод на текущем этапе

Основной кандидат — **локально запускаемый клиент**, а не единый hosted importer: это позволяет каждому пользователю проходить вход у провайдера на своём устройстве и не передавать его библиотеку серверу проекта. Интеграции должны иметь явный статус: официальный OAuth, пользовательская сессия/private API, файл экспорта или native local app. Не скрывать переход между этими способами.

Строгая цель «одна кнопка, все аккаунты, без credentials автора» пока не доказана. Самые важные проверки — подтвердить бесплатный локальный write в Apple Favorite Songs, полноту лайков Звука и подобрать для Яндекса вход с минимальными scopes; проверенный Android Device Flow consent оказался слишком широким. Для Spotify нужно выбрать честный путь между ручным архивом и неофициальным Web Player API. Если единственный путь требует shared app credentials разработчика или несоразмерные permissions, это считается архитектурным несоответствием цели, а не незаметной предпосылкой реализации.

## Где запускать красивый интерфейс

| Вариант | Запуск и интерфейс | Доступ к уже открытой сессии провайдера | Ограничения / роль |
|---|---|---|---|
| GitHub Pages | Самый быстрый общий URL; можно сделать красивый адаптивный веб-интерфейс. | Обычная веб-страница не получает права расширения на вкладки и cookies. Она также упирается в CORS и правила браузера при запросах к чужим доменам. | Только статический HTML/CSS/JS, без backend. Подходит для лендинга, инструкций, демонстрации UI и загрузок. Не хранить там пользовательские токены или музыкальные данные; GitHub отдельно ограничивает использование Pages как бесплатного хостинга SaaS. |
| Chrome extension, Manifest V3 | Установка один раз; полноэкранная страница расширения может выглядеть как приложение, а не тесный popup. Работает в поддерживаемом Chromium-браузере. | Может по нажатию пользователя подключаться к вкладке сервиса через `activeTab`/`scripting`; расширению нужны явно объяснённые разрешения на сайты. Запросы и данные остаются на устройстве. | Сильный первый прототип, но бесплатное распространение имеет UX-компромисс: публикация в Chrome Web Store требует регистрации разработчика и разового сбора; бесплатная альтернатива — скачивание исходников/архива и ручная установка `Load unpacked` с включённым Developer mode. Не использовать широкое чтение cookies, если запрос можно выполнить из контекста вкладки. |
| Локальный desktop companion | Скачал/запустил приложение; удобная полноценная очередь переноса, журнал и системное хранилище секретов. | Сам по себе не наследует Chrome-сессию; нужен локальный extension connector, поддерживаемый вход OAuth или ручной импорт файла. | Наиболее гибкий конечный контейнер и кандидат для интеграции с Music.app, но сборка и установка под каждую ОС сложнее. Chrome Native Messaging — отдельный мост, который требует установленного приложения и регистрации host. |

**Рекомендация с учётом запуска «быстро и красиво»: GitHub Pages сделать публичным входом в проект** — аккуратный адаптивный лендинг, демонстрация интерфейса, проверка совместимости, краткие инструкции и кнопки загрузки релиза. Сам импортёр делать как dashboard внутри Chrome extension: страницу Pages нельзя превратить в мост к чужим авторизованным вкладкам одним JavaScript, а статический Pages не даёт backend. Расширение после явного нажатия работает с открытой вкладкой источника, сначала получает и сверяет лайки, затем показывает предпросмотр совпадений и просит отдельное подтверждение на запись. Так интерфейс остаётся красивой самостоятельной страницей, а сессии и библиотека остаются у пользователя.

Для бесплатного распространения релиз можно публиковать на GitHub и устанавливать распакованным архивом с Developer mode; это добавляет ручной шаг. Однонажаточная установка Chrome Web Store проще пользователю, но требует платной регистрации издателя, так что сейчас не соответствует условию «не платить». Если понадобится запись через Music.app, добавить небольшой необязательный локальный companion. Не выдавать Pages за готовый multi-provider importer и не отправлять секреты в `localStorage`/GitHub Pages.

Это решает лёгкость запуска для первой целевой группы, уже использующей Chrome, но не всех: пользователю другого браузера понадобится desktop/Firefox вариант, а пользователю Apple Music в браузере всё равно может понадобиться developer token. Apple подтверждает, что MusicKit Web автоматически ведёт Music User Token для запросов пользователя, но API также требует developer token; это пока главный открытый вопрос для простого входа без credentials автора. До выбора UI необходимо закончить проверку локальной записи Favorite Songs через Music.app и убедиться, что browser connector может читать все нужные лайки без извлечения/сохранения cookies.

Технические основания: [GitHub Pages — что это](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), [ограничения Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), [разрешения расширений Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), [регистрация Chrome Web Store разработчика](https://developer.chrome.com/docs/webstore/register/), [установка распакованного расширения](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load-unpacked), [Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), [Apple MusicKit user auth](https://developer.apple.com/documentation/applemusicapi/user-authentication-for-musickit), [Apple developer tokens](https://developer.apple.com/documentation/AppleMusicAPI/generating-developer-tokens).

## Ближайшая последовательность

1. Зафиксировать минимальные пользовательские данные каждого источника и API/auth route в provider inventory.
2. Проверить локальный Apple Music.app Favorite Songs write/read-back на одной явно выбранной тестовой записи.
3. Повторно проверить полноту курсорного экспорта Звука и найти least-privilege авторизацию Яндекс Музыки; не использовать широкий Android client consent как готовый путь.
4. Сравнить для Spotify API PKCE, Account Data archive и Web Player session по UX, устойчивости, правилам и зависимости от app owner.
5. После этого проверить Chrome extension dashboard как первый UX; Pages использовать для проекта и документации, не для обхода ограничений браузера или хранения авторских credentials.
