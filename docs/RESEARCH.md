# Исследование музыкального импорта

Дата первичного обзора: 27 октября 2026. Это рабочая техническая карта, не обещание неизменности API: у нескольких провайдеров эндпоинты и условия доступа меняются без обратной совместимости.

Для быстрого просмотра конкретных migration-related HTTP и GraphQL вызовов см. [сводный каталог API-маршрутов](API_MATRIX.md); здесь остаются выводы, trade-offs и план незакрытых проверок.

Для сравнения идентификаторов между source API и Apple catalog, ISRC fallback и безопасной ручной проверки есть отдельная [заметка по сопоставлению](MATCHING.md).

Для Яндекс Музыки добавлен отдельный [полный индекс pinned community OpenAPI](providers/yandex-openapi-inventory.md): 150 HTTP operations из 144 path templates, сгруппированные по областям API.

Для Spotify добавлен [полный индекс официального OpenAPI](providers/spotify-openapi-inventory.md): 96 операций из 70 path templates с OAuth scopes и флагами deprecation.

## Цель

Переносить сохранённые треки (лайки), а затем плейлисты и прочие элементы библиотеки из Звука, Spotify и Яндекс Музыки в Apple Music. Требования: без платных агрегаторов, без искусственного лимита на объём миграции, аккуратное сопоставление версий треков, понятный список несовпадений, простой вход в свои аккаунты и запуск без developer credentials автора проекта. Предпочтительна локальная обработка пользовательских токенов и библиотеки. Перенос аудиофайлов не требуется: API работают с каталогами и записями библиотек, а не дают право переносить потоковые аудиофайлы между сервисами.

Желаемый простой UX упирается в реальные ограничения: Spotify Development Mode и Apple Music REST зависят от developer credentials владельца приложения. Эти зависимости нельзя прятать или выдавать за «вошёл в аккаунт — всё работает». Текущие обходные/локальные кандидаты и критерии выбора зафиксированы в [направлении продукта](PRODUCT_DIRECTION.md).

## Краткий вывод

- Для Spotify есть официальный Web API с OAuth PKCE и доступом к сохранённым трекам; полный route inventory сформирован из официальной OpenAPI спецификации. Developer Policy §I.9 прямо описывает исключение для передачи личных данных пользователя или метаданных его плейлистов в другой сервис; проект должен следовать остальным Developer Terms, а применение к конкретной реализации отдельно не подтверждено. Пользователь разрешил принять Developer Terms и создать приложение при Premium, но Account Overview показывает сбой оплаты и скорую потерю доступа, а видимый checkbox условий не реагирует на обычный клик через browser control. Условия не приняты, app не создан и OAuth не запускался. Development Mode требует active Premium у владельца app и ограничен одним Client ID/пятью пользователями.
- У Apple есть встроенный импорт с доступными провайдерами в iOS/Android и на web. Apple прямо пишет: лайки из исходного сервиса идут в Favorite Songs. Нужна подписка Apple Music, Sync Library, подходящий регион и наличие нужного source в списке; трансфер реализует third party, поэтому проверить его для конкретных аккаунтов и объёмов.
- Apple Music REST API умеет добавлять именно в Favorites (`POST /v1/me/favorites`), отдельно от Library add, но developer token требует участия в Apple Developer Program ($99/год). Отдельный legacy iTunes Search API всё ещё ответил `200` без авторизации из чистого терминального запроса и годится как бесплатный генератор текстовых кандидатов; проверенный результат не содержал ISRC, а `trackId` не доказан как Apple Music catalog ID. В локальном Music.app read-only AppleScript-проверка подтвердила чтение поля `favorited` и подсчёт избранного без вывода личных значений. Полный бесплатный цикл каталожного импорта ещё не доказан: у `applemusic-mcp` catalog → Library требует network/API, а его native setter использует старое имя `loved` при том, что текущий Music.app SDEF объявляет `favorited`. Write/read-back на тестовой записи и облачная синхронизация не проверены.
- Для Яндекс Музыки есть зрелая, активно документируемая сообществом Python-библиотека и OAuth Device Flow, но API неофициальный. Device-code request проверен в терминале; consent screen Android client запросил музыкальные scopes вместе с профилем, платежами, Яндекс.Диском и умным домом. Согласие отменено до получения токена; для проекта этот OAuth flow пока слишком широк. Отдельно clean-terminal cookie-only `GET /account/status` и `/users/{uid}/likes/tracks` проверены через три выбранных Chrome auth cookies: оба ответа `200`; этот read-only private path не требует OAuth app ID.
- Для Звука найден актуальный community-клиент `trudenboy/zvuk-music` (MIT, PyPI): `get_liked_tracks()`, `like_track()` и `unlike_track()` поверх GraphQL. Библиотека утверждает, что полный доступ требует пользовательский токен и платную подписку, но разделение подписочных требований для чтения лайков неочевидно — нужно проверить read-only. У пользователя `ZvukDownloader` и `Aiving/sberzvuk-api` методов лайков не найдено.
- Cross-check `trudenboy/ma-provider-zvuk-music`, HEAD `8a9058928e7d80822717337d364e6c8abefc4b78` (2026-10-27): Music Assistant оборачивает `zvuk-music`, вручную принимает user token из `/api/tiny/profile`, вызывает `get_collection()`/`get_liked_tracks()` и имеет like/unlike writes. Он ставит лимит пять запросов/с и backoff 60 s при 429, а batches по 50 применяет при гидрации metadata. Это не доказывает полноту likes list: underlying `userTracks` остаётся без cursor pagination; проект статически просмотрен, не запускался.
- Свежая проверка frontend Звука, 27.10.2026: чистый terminal GET `/favorites` получил `200`, но body был Servicepipe challenge shell без Next runtime; публичный CDN build manifest и все 100 JS chunks build `v8.20.1` получили `200` без cookies (около 2.17 MB). Статический UI inventory обнаружил `getProfileFavoritesInfo`, cursor `getPaginatedCollection`/`getPaginatedCollectionAll`, `getPaginatedCollectionAllSections`, `getCollectionIds`, `getCollectionCount` и `getTracksShortInfo`; это имена service layer, не гарантированные backend GraphQL operation names. Значение `limit=30` совпало с прежним browser capture; `/collection` также использует section fetch с `limit=15`. Новая Chrome-вкладка показывала анонимное `0 треков`, GraphQL request там не наблюдался — это не свидетельство пустой авторизованной библиотеки и не новый authenticated API test. Добавлены детали в `docs/providers/zvuk-api-inventory.md`.
- Новый cross-platform кандидат `xlollx/Songport`, GPL-3.0-only, HEAD `5aba73a` (2026-10-27): local-first Android app, encrypted on-device tokens, Spotify Web Player sign-in/private GraphQL route и Apple Music WebView token bridge. README помечает оба web paths как unofficial/unstable; официальные Spotify/Apple connectors всё равно требуют app credentials. Songport умеет Spotify liked songs и Apple playlists/library, но не объявляет Apple Favorite Songs как destination и не поддерживает Яндекс/Звук; это UX/architecture reference, не готовое решение. Проверен статически, не запускался.
- Проверен новый локальный UX-reference `OleksandrS23/Spotify2Yt`, MIT, HEAD `03225fc` (2026-10-01): Playwright запускает отдельный persistent Chrome/Edge profile, ждёт вход пользователя, перехватывает Spotify web-player Bearer в памяти и читает `GET /v1/me/tracks`; если запрос не проходит, пробует DOM scroll на Liked Songs. Приложение ограничивает Flask localhost (`127.0.0.1`) и сохраняет browser profile, Spotify CSV, progress, YouTube Music auth JSON и лог в user data dir. Это реальное доказательство UX без developer app и без доступа к обычному Chrome profile, но не Apple/Yandex/Zvuk adapter; private web token и DOM fallback нестабильны, а code содержит automation-hiding flags, которые мы не переносим. Статически проверены README, source и MIT license, приложение не запускалось.
- Проверен GitHub-кандидат `sohsatoh/Apple-Music-Importer`, MIT, HEAD `147eedb` от 2025-02-24: читает Spotify `liked` через `current_user_saved_tracks` offset pagination, ищет Apple catalog по ISRC и тексту, добавляет через `POST /v1/me/library` или создаёт обычный playlist. В CLI требуется скопировать Apple web-player request headers в JSON и отдельно настроить Spotify Developer OAuth credentials; автоматического пользовательского входа нет. Он не пишет Apple Favorite Songs, не поддерживает Яндекс/Звук, хранит найденные треки локально и кэширует даже POST на сутки. MIT/source статически проверены, приложение не запускалось.
- У Звука есть официальная миграция **в Звук** из Spotify, Яндекс Музыки, Apple Music, VK, Deezer и YouTube Music. Она создаёт отдельный плейлист, а не «Любимое», и переносит только треки из каталога Звука. Официальная справка прямо сообщает, что экспорт из Звука пока недоступен. Поэтому для направления Звук → Apple нужен отдельный read-only источник лайков (кандидат — `zvuk-music`) и собственная запись в Apple Favorites.
- Нашли два точных open-source пути для лайков: `yarikmsu/yandex-music-transfer` реализует Яндекс → Apple Favorite Songs, а `ahnafnafee/songmirror` реализует Spotify → Apple Favorite Songs и несколько других сервисов. Оба технически попадают в нужную коллекцию, но используют web-session токены вместо только официальных OAuth интеграций; Apple library всё равно требует подходящую подписку. SongMirror не поддерживает Яндекс/Звук, а Yandex Music Transfer не является полноценным источником для Звука. Единого проверенного бесплатного переносчика всех трёх источников в Apple Favorites пока не найдено.

## Предлагаемая схема приложения

1. **Адаптер источника** авторизуется с минимальными разрешениями и отдаёт нормализованные элементы с исходными ID, названием, артистами, альбомом, длительностью, ISRC (если доступен), явностью/версией, датой и исходным порядком.
2. **Нормализованный экспорт** сохраняется локально как JSON/SQLite. Секреты и сами токены отделяются от каталога и не попадают в экспорт/логи.
3. **Сопоставление с каталогом Apple**: сначала ISRC, затем поиск по артисту/названию/альбому и длительности; учитываются версии (live/remaster/clean/explicit), региональный storefront и дубликаты. Неуверенные результаты оставляются для ручного выбора.
4. **Предпросмотр** показывает точные совпадения, спорные варианты, отсутствующие записи и потенциальные дубликаты до записи в библиотеку.
5. **Идемпотентная запись**: проверить, что песня не добавлена повторно; добавить лайки небольшими пачками; перепроверить результат и сохранить отчёт. Для API с лимитами использовать пагинацию, backoff на 429 и продолжение после сбоя.
6. **Восстановление**: исходный экспорт не изменяется. В отчёте остаются исходные ID и соответствия Apple, чтобы можно было повторить перенос или удалить только добавленные приложением элементы.

## Что означает «без ограничений» на практике

Нельзя гарантировать отсутствие ограничений со стороны сервисов. Реалистичная цель — не вводить собственный лимит количества треков: проходить пагинацию, батчировать запросы, продолжать с места сбоя и не терять непривязанные элементы. Но провайдеры могут ограничить приложение, доступ к отдельным аккаунтам, частоту запросов, регион каталога, членство/подписку и размер одного запроса. У Spotify Development Mode есть ограничения. Встроенный Apple transfer — лучший кандидат для проверки Spotify → Apple без отдельного API-клиента; Spotify archive export — бесплатный резервный источник. Для Звука и Яндекса остаётся локальная сборка коннекторов.

## Практические проверки и оставшиеся шаги

- Сделано: исходный код и документацию основных клиентов, `Yandex Music Transfer`, `SongMirror` и `Spotify Account Migrator` просмотрели статически; точные Apple Favorite Songs calls, Spotify Web API changes февраля 2026, auth-пути, лицензии и ограничения занесли в `docs/providers/` и `docs/PROJECTS.md`. Сторонний код не запускали.
- Сделано read-only: в Chrome наблюдали web API маршруты всех четырёх сервисов. В чистом терминальном HTTP-клиенте с временной сессией Яндекса успешно прочитали account status, полный список liked track refs и одну метаданную карточку; для Звука прошли `userTracks` и `getTracks`. Ответы обработаны в памяти; track IDs, названия, UID и размер коллекций в GitHub не сохранялись.
- Новая read-only проверка Spotify Web Player в Chrome: POST persisted-query GraphQL `fetchPlaylistContents` на `api-partner.spotify.com/pathfinder/v2/query` вернул 200; ответ имеет offset/limit paging и `totalCount`. На странице также наблюдались `libraryV3`, `fetchPlaylist`, `fetchPlaylistMetadata`, `playlistPermissions`, `areEntitiesInLibrary` и `isCurated`; `spclient.wg.spotify.com/collection/v2/contains`, `/extended-metadata/v0/extended-metadata` и `/library-import/v1/eligible` отвечали 200. Сохранили только маршруты, названия операций, ключи переменных/полей и статусы; значения URI, user, заголовков, содержимое, ID и размеры коллекции не сохранялись. Это private web-player API, не официальный Web API.
- Полная read-only пагинация Spotify Web Player проверена из терминала: `fetchPlaylistContents`, последовательные `offset` при `limit=50` до API `totalCount`; все страницы вернули 200 и server paging совпал с запросом. Фактический count и персональные записи не выводились/не фиксировались. Первый replay с урезанными заголовками получил 403, точный набор нужных браузерных заголовков позволил пройти все страницы. Временный файл `0600` удалён.
- Новое локальное Apple-подтверждение: установленный Music.app объявляет writable `track.favorited` (`pLov`) в системном SDEF; clean terminal `osascript` смог прочитать `favorited` у существующего трека и успешно выполнить `(every track whose favorited is true)`. Число/названия подавлены и не сохранялись; библиотека не экспортировалась, состояние треков не меняли. SDEF показывает `search` внутри playlist и файловую команду `add`, но не подтверждает каталоговый поиск/добавление cloud-track из AppleScript.
- Live UI Apple Transfer: повторно открыт пункт `Transfer Music` из меню авторизованной страницы. Появилась оболочка `Select a Music Service`, но внутри снова показано `Transfer Service is Busy`; список источников не отрисовался. Поддержка Spotify/Яндекса/Звука для данного аккаунта не выяснена; source accounts не подключались, перенос не запускался.
- Новый GitHub-кроссчек Яндекса: текущий `trudenboy/ma-provider-yandex-music` вызывает `users_likes_tracks()` из `yandex-music`, умеет like/unlike и сортирует лайки по времени. Это подтверждает библиотечный путь, но не полный экспорт: его виртуальный playlist возвращает только первую страницу и режет список до default 200 / configurable 50–2000. Зафиксировано как ограничение стороннего UI, не API. Также замечены противоречия в самом проекте: default 500 в feature-doc, 200 в коде; README license Apache-2.0, `LICENSE`/GitHub metadata MIT.
- Новый прямой GitHub-кандидат Spotify → Apple: `nedu-m/spotify-to-apple-music` на HEAD `0590af0` объединяет официальный Spotify PKCE/export и Apple ISRC matching/checkpoints, но лицензии не объявляет и получает Apple developer token из web-player JS (README признаёт несоответствие Apple Terms). Его команда `favourite` вызывает Apple `/me/ratings/songs/{id}` с value `1`, а не официальный `/me/favorites`; Apple docs и Music.app SDEF разделяют rating и Favorite Songs. Не запускается как готовый Favorite Songs importer.
- Границы доступа также подтверждены: Spotify официальный Web API без OAuth отвечает `401`; web-player token endpoint вернул `403`, но точный read-only GraphQL `fetchPlaylistContents` успешно replay-нут в терминале с browser bearer + client-token (`200`, JSON, без GraphQL errors). Apple GET к `/me/library/songs` с одним лишь Music User Token cookie ответил `401`; с парой `Authorization` + `Media-User-Token`, взятой из активного Apple web-player запроса, чистый terminal GET к `/me/library/playlists?limit=1` и одному элементу системного Favorite Songs ответил `200`. Яндекс no-auth search и authenticated cookie-only account/likes GETs отвечают `200`.
- Не выполнено: Apple built-in transfer для конкретного аккаунта и небольшой фактический перенос. Это отдельное действие, меняющее библиотеку Apple.
- Частично выполнено: Yandex и Zvuk private read endpoints из терминала возвращают списки лайков. Не выполнено: сохранённый нормализованный экспорт, независимая сверка полноты/пагинации, тест чтения Звука без платного тарифа и чтение Spotify через официальный OAuth.
- Сделано по документации: Spotify Authorization Code + PKCE authorize/token/refresh параметры, минимальный scope `user-library-read`, loopback redirect и lifetime access/refresh token записаны в `docs/providers/spotify.md`. Не выполнено на практике: зарегистрировать/выбрать приложение, провести redirect/callback, обменять код и пройти read-only pagination через `GET /me/tracks`; это зависит от Spotify Developer Mode и ещё не запускалось.
- Spotify archive cross-check: официальная справка подтверждает `Your Library` (saved songs, episodes, shows, artists, albums и URIs); `liMusic`, `Namida` и `MelodyBridge` независимо читают `YourLibrary.json` как `tracks[]` с типичными полями `artist`, `album`, `track`, `uri`, а MelodyBridge явно называет это источником liked songs. В Spotify Account Privacy UI выбрано только `Account data`; он указывает 5 дней подготовки и требует подтвердить запрос по email, при этом пакет включает и другие персональные категории. Запрос ожидает подтверждения; расширенная история не запрашивалась, ZIP ещё не получен/не проверен. После подтверждения читать только `YourLibrary.json`, вариации схемы и полноту архива сверить без сохранения ZIP/других данных.

### Яндекс cookie-session и Track metadata повторная проверка (27.10.2026)

- В обычном terminal HTTP-клиенте с выбранными локально Chrome cookies `Session_id`, `sessionid2`, `i` endpoints `/account/status` и `/users/{uid}/likes/tracks` вернули `200`. `library.tracks` в ответе пришёл одним массивом: у всех returned short refs был ID, повторов не обнаружено, `revision` присутствовал, pagination fields не было. Это не независимая сверка с UI count или экспортом; значения и размер списка не сохранялись.
- Сравнительный terminal probe: `if-modified-since-revision=<текущая revision>` вернул `200` со строковым `result` без `library`; запрос с revision на единицу меньше вернул `200` с объектом `library` и `tracks[]`. Это подтверждает на текущем аккаунте, что устаревшая revision возвращает полный список, а совпадающая не переотдаёт его. Строковый ответ и полный conditional-sync контракт официально не описаны; pinned community client возвращает `None` для non-dict ответа, а семантика parameter в исходнике помечена TODO.
- `POST /tracks` с form-urlencoded `track-ids` подтвердил batch sizes 1, 10, 20 и 25: `200`, response array совпадал с количеством запрошенных Track objects; ISRC не встретился в authenticated sample первых 25 ID. Probe на 30 IDs превысил timeout, 100-ID запрос получил сетевой сбой. Жёсткий limit не установлен; размер 25 сейчас подтверждён для экспорта, больший batch требует отдельно бережно измерить.
- Статически проверен `MarshalX/yandex-music-token` HEAD `4d90e6b`: расширение запускает OAuth implicit redirect, читает token fragment и перенаправляет token в Telegram bot URL. OAuth app-info endpoint перечислил 19 scopes, включая лишние профиль/payments/Disk/smart-home права; extension не устанавливался и OAuth не запускался.
