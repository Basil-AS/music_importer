# Исследование музыкального импорта

Дата первичного обзора: 27 октября 2026. Это рабочая техническая карта, не обещание неизменности API: у нескольких провайдеров эндпоинты и условия доступа меняются без обратной совместимости.

Для быстрого просмотра конкретных migration-related HTTP и GraphQL вызовов см. [сводный каталог API-маршрутов](API_MATRIX.md); здесь остаются выводы, trade-offs и план незакрытых проверок.

Для сравнения идентификаторов между source API и Apple catalog, ISRC fallback и безопасной ручной проверки есть отдельная [заметка по сопоставлению](MATCHING.md).

Для Яндекс Музыки добавлен отдельный [полный индекс pinned community OpenAPI](providers/yandex-openapi-inventory.md): 150 HTTP operations из 144 path templates, сгруппированные по областям API.

Для Spotify добавлен [полный индекс официального OpenAPI](providers/spotify-openapi-inventory.md): 96 операций из 70 path templates с OAuth scopes и флагами deprecation.

Для Apple Music сформирован [полный официальный REST endpoint index](providers/apple-openapi-inventory.md) из актуального Apple Developer DocC: 138 документированных операций и 119 уникальных method/path пар, включая параметры, ответы и auth-контекст.

## Цель

Переносить лайки/избранное, плейлисты и другие поддерживаемые элементы пользовательских библиотек **между любыми двумя** из Звука, Spotify, Яндекс Музыки и Apple Music во всех направленных комбинациях. При подключении account автоматически обнаруживать коллекции и все их страницы; не загружать целиком глобальный музыкальный каталог провайдера. Автоматически сопоставлять массовые списки, оставляя ручную проверку только для неоднозначных результатов. Требования: без платных агрегаторов, искусственного лимита и author-owned credentials; точное сопоставление версий треков, понятные несовпадения, простой вход и безопасный resume. Сохранять нативный тип коллекции, а playlist fallback предлагать отдельно и только с выбором пользователя. Предпочтительна локальная обработка пользовательских токенов и библиотеки. Перенос аудиофайлов не требуется: API работают с каталогами и записями библиотек, а не дают право переносить потоковые аудиофайлы между сервисами.

Желаемый простой UX упирается в реальные ограничения: Spotify Development Mode и Apple Music REST зависят от developer credentials владельца приложения. Эти зависимости нельзя прятать или выдавать за «вошёл в аккаунт — всё работает». Текущие обходные/локальные кандидаты и критерии выбора зафиксированы в [направлении продукта](PRODUCT_DIRECTION.md).

## Краткий вывод

- Для Spotify есть официальный Web API с OAuth PKCE и доступом к сохранённым трекам; полный route inventory сформирован из официальной OpenAPI спецификации. Developer Policy §I.9 прямо описывает исключение для передачи личных данных пользователя или метаданных его плейлистов в другой сервис; проект должен следовать остальным Developer Terms, а применение к конкретной реализации отдельно не подтверждено. Пользователь разрешил принять Developer Terms и создать приложение при Premium, но Account Overview показывает сбой оплаты и скорую потерю доступа, а видимый checkbox условий не реагирует на обычный клик через browser control. Условия не приняты, app не создан и OAuth не запускался. Development Mode требует active Premium у владельца app и ограничен одним Client ID/пятью пользователями.
- У Apple есть встроенный импорт с доступными провайдерами в iOS/Android и на web. Apple прямо пишет: лайки из исходного сервиса идут в Favorite Songs. Нужна подписка Apple Music, Sync Library, подходящий регион и наличие нужного source в списке; трансфер реализует third party, поэтому проверить его для конкретных аккаунтов и объёмов.
- Apple Music REST API умеет добавлять именно в Favorites (`POST /v1/me/favorites`), отдельно от Library add, но developer token требует участия в Apple Developer Program ($99/год). Отдельный legacy iTunes Search API всё ещё ответил `200` без авторизации из чистого терминального запроса и годится как бесплатный генератор текстовых кандидатов; проверенный результат не содержал ISRC, а `trackId` не доказан как Apple Music catalog ID. В локальном Music.app read-only AppleScript-проверка подтвердила чтение поля `favorited` и подсчёт избранного без вывода личных значений. Полный бесплатный цикл каталожного импорта ещё не доказан: у `applemusic-mcp` catalog → Library требует network/API, а его native setter использует старое имя `loved` при том, что текущий Music.app SDEF объявляет `favorited`. Write/read-back на тестовой записи и облачная синхронизация не проверены.
- Новый Apple destination/UI reference `Skalas/music-sync`, pinned HEAD `9f961d9e439885eaff6dff6da125e238f278da6e` (2026-10-09): local FastAPI/TypeScript dashboard, SQLite, dry-run default; Apple likes read/write через Music.app AppleScript, отсутствующие songs импортируются вручную созданным iTunes Store Shortcut, затем AppleScript повторно проверяет Library. Это локальный путь без Apple developer token для favorite setter, но не без авторской зависимости целиком: Spotify требует пользовательский OAuth app, Tidal — отдельный Client ID; Яндекса/Звука нет. Гитхаб не указывает лицензию и в checkout нет `LICENSE`, поэтому код не копировать. Статически просмотрены README/provider/scripts/UI, auth и writes не запускались.
- На этом Mac `osacompile` успешно скомпилировал обе его AppleScript процедуры чтения/выставления `favorited`; локальный SDEF подтверждает boolean `track.favorited` (`pLov`). Компиляция подтвердила только синтаксис, скрипты не исполнялись, Music.app automation permission не запрашивалось, состояние коллекции не менялось.
- Для Яндекс Музыки есть зрелая, активно документируемая сообществом Python-библиотека и OAuth Device Flow, но API неофициальный. Device-code request проверен в терминале; consent screen Android client запросил музыкальные scopes вместе с профилем, платежами, Яндекс.Диском и умным домом. Согласие отменено до получения токена; для проекта этот OAuth flow пока слишком широк. Отдельно clean-terminal cookie-only `GET /account/status` и `/users/{uid}/likes/tracks` проверены через три выбранных Chrome auth cookies: оба ответа `200`; этот read-only private path не требует OAuth app ID.
- Для Звука найден community-клиент `trudenboy/zvuk-music` (MIT, PyPI): `get_liked_tracks()`, `like_track()` и `unlike_track()` поверх GraphQL. Свежая сверка HEAD `ed491f61bc7b18c9f327017a8a87d9fe183022a7` подтвердила: его `userTracks` передаёт только параметры сортировки и не имеет cursor/page loop; cursor-пагинатор в этом же клиенте реализован только для podcasts. Готовый `get_liked_tracks()` поэтому нельзя считать полным экспортом большой коллекции без count/ID сверки. Заявление README о платной подписке пока не разделено на чтение лайков и качество воспроизведения; проверить read-only на аккаунте без подписки, если такой доступен. У пользователя `ZvukDownloader` и `Aiving/sberzvuk-api` методов лайков не найдено.

У отдельных старых клиентов — cookie `auth` | Неофициальный, недокументированный провайдером | Автор библиотеки указывает платную подписку для полного доступа; нужен read-only тест лайков без неё. Token — секрет сессии |

## Предлагаемая схема приложения

1. **Адаптер источника** авторизуется с минимальными разрешениями и отдаёт нормализованные элементы с исходными ID, названием, артистами, альбомом, длительностью, ISRC (если доступен), явностью/версией, датой и исходным порядком.
2. **Нормализованный экспорт** сохраняется локально как JSON/SQLite. Секреты и сами токены отделяются от каталога и не попадают в экспорт/логи.
3. **Сопоставление с каталогом Apple**: сначала ISRC, затем поиск по артисту/названию/альбому и длительности; учитываются версии (live/remaster/clean/explicit), региональный storefront и дубликаты. Неуверенные результаты оставляются для ручного выбора.
4. **Предпросмотр** показывает точные совпадения, спорные варианты, отсутствующие записи и потенциальные дубликаты до записи в библиотеку.
5. **Идемпотентная запись**: проверить, что песня не добавлена повторно; добавить лайки небольшими пачками; перепроверить результат и сохранить отчёт. Для API с лимитами использовать пагинацию, backoff на 429 и продолжение после сбоя.
6. **Восстановление**: исходный экспорт не изменяется. В отчёте остаются исходные ID и соответствия Apple, чтобы можно было повторить перенос или удалить только добавленные приложением элементы.

## Что означает «без ограничений» на практике

Нельзя гарантировать отсутствие ограничений со стороны сервисов. Реалистичная цель — не вводить собственный лимит количества треков: проходить пагинацию, батчировать запросы, продолжать с места сбоя и не терять непривязанные элементы. Но провайдеры могут ограничить приложение, доступ к отдельным аккаунтам, частоту запросов, регион каталога, членство/подписку и размер одного запроса. У Spotify Development Mode есть ограничения. Встроенный Apple transfer — лучший кандидат для проверки Spotify → Apple без отдельного API-клиента; Spotify archive export — бесплатный резервный источник. Для Звука и Яндекса остаётся локальная сборка коннекторов.
