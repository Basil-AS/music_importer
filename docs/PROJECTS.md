# Готовые проекты и повторное использование

Срез на 2026-10-28. Уровни проверки: upstream README, лицензии и GitHub metadata просмотрены; для `oklookat/synchro` дополнительно статически проверены account/transfer source files, код не запускался. По GitHub API upstream SongMirror имеет MIT license и последний push 2026-10-21; MarshalX/yandex2spotify — MIT, последний push 2026-03-18; trudenboy/zvuk-music — MIT, последний push 2026-10-07; ZvukDownloader license не объявляет, последний push 2026-02-13. Для SongMirror ранее дополнительно просмотрены исходники коннекторов и matching/cache modules. Готовый проект подходит только если покрывает Spotify, Apple Music, Яндекс Музыку и Звук, удобный пользовательский вход и локальное исполнение.

## SongMirror: что стоит перенять

Клонированный для чтения snapshot находится вне проекта в `/tmp/songmirror-review`. Смотрелись `engine/matching.py`, `engine/resolve_cache.py`, Spotify/Apple account connectors и transfer services; код не исполнялся и не копировался.

- Matching совмещает hard identifiers, RapidFuzz token scoring, Jaro-Winkler, transliteration и gates по performer/version/duration. Наш static matcher теперь добавляет кириллическую транслитерацию и удаляет `feat.` из title scoring без снижения автоматического порога.
- Resolve cache хранит пользовательские/автоматические mappings раздельно, наследует положительные результаты из родственных профилей и не наследует отрицательные ответы. Текущий IndexedDB cache хранит до 12 нормализованных кандидатов на успешный поиск или короткую отрицательную выдачу, учитывает storefront и public-preview/account режим Apple Music; совпадения живут 30 дней, пустая выдача 7 дней. Ручные запросы и сетевые ошибки не сохраняются; Yandex album ID сохраняется для последующей записи плейлиста. Решения по match/исключению хранятся отдельно до 180 дней и восстанавливаются только если прежний target ID присутствует в новых кандидатах. Локальный job journal теперь сохраняет recovery plan и поддерживает карту созданных целевых плейлистов, удаляя эти данные после успеха или ручной сверки; writers ещё не используют checkpoint для resume.
- Transfer orchestration у SongMirror включает progress, per-provider safety caps и history. Наш браузерный app хранит recovery plan локально и может продолжить запись у всех четырёх целей, если target playlist ID сохранён: writer сверяет точный префикс и добавляет остаток. Если ID не успел сохраниться или порядок расходится, требуется ручная сверка. Критичные требования для тысяч треков остаются: bounded batches, provider rate-limit profiles и precision/recall метрики на реальных совпадениях; никакой live end-to-end transfer ещё не подтверждён.
- Spotify `sp_dc` и Apple Music token paste убирают developer app setup, но заставляют пользователя вручную вытаскивать секреты из DevTools. Наше расширение сохраняет более простой UX: команды отправляются в уже авторизованную вкладку, без чтения cookie database и копирования bearer tokens в приложение.

## Требования к интеграции проектов

Ни один найденный проект не закрывает одновременно Spotify, Apple Music, Яндекс Музыку и Звук для likes и playlists во всех направлениях с чистым пользовательским входом и локальным исполнением. `synchro` заявляет likes для всех четырёх, но README не заявляет playlists или простой GUI; Songport и SongMirror имеют более зрелый transfer UX, но не закрывают два российских сервиса или требуют ручного копирования credentials. Официальная миграция Звука полезна для части входящих playlists, но не переносит likes в «Любимое» и не экспортирует из Звука. Поэтому локальная extension-архитектура остаётся подходящей базой, а проекты используются как независимые API/matching/workflow references.

Прежде чем заимствовать код, фиксировать источник файла/алгоритма, лицензию репозитория и runtime dependency, затем сохранять upstream attribution. Для реализации сервиса нужны отдельные evidence по login, полной пагинации likes/playlists, поиску целевого каталога, записи и read-back; README или fixture сами по себе live-совместимость не подтверждают.
