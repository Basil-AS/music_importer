# Матрица переноса между сервисами

Срез 28.10.2026. Эта матрица отделяет существование маршрута от проверенного end-to-end переноса. «Чтение» означает пользовательскую библиотеку/коллекции, а не глобальный каталог стриминга. `Есть` означает, что маршрут подтверждён официальной документацией или исходником; `Частично` — есть нерешённый вопрос полноты/совместимости; `Не проверено` — запись в пользовательский аккаунт не выполнялась.

## Возможности каждого сервиса

|---|---|---|---|---|---|

Это native Saved Tracks. | **Есть, не проверено записью:** `POST /v1/me/playlists`, затем `POST /v1/playlists/{id}/items`; новые paths и payload semantics нужно соблюдать после миграции февраля 2026. | **Частично:** официальный Web API требует app Client ID; Development Mode требует Premium у владельца app и сейчас допускает до 5 пользователей. ## Все направленные пары

На уровне API-шаблонов source-read и target-write операции существуют у всех четырёх сервисов, так что все 12 комбинаций имеют технические кандидаты для likes и playlists. Ни одна пара пока не является готовой функцией продукта: ни для одного target не выполнен полный тестовый transfer с обратным чтением, а вход/полнота отдельных источников остаются условными. Клетка показывает, какие adapter gaps надо закрыть для конкретного направления; это не обещание, что API допустим или стабилен.

| Источник → назначение | Spotify | Apple Music | Яндекс Музыка | Звук |
|---|---|---|---|---|
| **Spotify** | — | Spotify read/auth частично private; Apple write/key blocked | Spotify read/auth частично private; Яндекс source completeness и auth | Spotify read/auth частично private; Звук write schema/auth |
| **Apple Music** | Apple source read найден; Spotify write OAuth/owner constraint | — | Apple source read найден; Яндекс destination auth/write verification | Apple source read найден; Звук destination auth/write verification |
| **Яндекс Музыка** | Яндекс source paging/auth incomplete; Spotify write OAuth/owner constraint | Яндекс source paging/auth incomplete; Apple write/key blocked | — | Яндекс source paging/auth incomplete; Звук destination auth/write verification |
| **Звук** | Звук read count mismatch/auth; Spotify write OAuth/owner constraint | Звук read count mismatch/auth; Apple write/key blocked | Звук read count mismatch/auth; Яндекс destination auth/write verification | — |

У каждого направления те же типовые задачи остаются отдельно для likes и playlist items. Для playlists требуется сохранить порядок, повторяющиеся записи и доступность; для favorites — не подменять нативную коллекцию обычным playlist без выбора пользователя. Треки, которых нет в каталоге назначения, должны остаться в отчёте пропусков, а не исчезнуть из количества.

## Сопоставление больших библиотек

Чтобы не сверять тысячи записей вручную, общий engine должен:

1. Сохранять исходный provider ID и использовать его для повторов и дубликатов; использовать ISRC там, где обе стороны его раскрывают.
2. Нормализовать Unicode, регистр, пунктуацию и метки версий (live/remaster/radio edit), затем ранжировать кандидатов по названию, артистам, альбому, длительности и региональной доступности.
3. Автоматически принимать только кандидаты выше откалиброванного high-confidence порога; показывать компактный review queue лишь для коллизий/низкой уверенности.
4. На каждой странице сохранять cursor/checkpoint. Для source totals сверять `total`, count и уникальные IDs; если API противоречит сам себе, не объявлять экспорт полным.
5. После batch writes прочитать назначение обратно, подтвердить фактические items и продолжать с последнего проверенного checkpoint после ошибки/429.

Никакой API ещё не демонстрирует сквозную end-to-end автоматизацию тысяч композиций в приложении Music Importer. Из текущих источников Spotify и Apple дают лучшие документированные каталожные идентификаторы; Yandex/Zvuk могут требовать metadata scoring, а Звук не возвращает `isrc` в проверенной Track GraphQL schema. Поэтому порог авто-переноса надо калибровать по test fixtures и не обещать 100% автоматического exact match.

## Приоритет реализации

1. Завершить единый provider adapter contract: `connect`, paged `discoverCollectionPage`, `readCollectionPage`, `searchTracks`, `readDestination`, `writeFavorites`, `createPlaylist`, `writePlaylistItems`, `readBack`, `disconnect`. PR #2 содержит общий cursor reader/search orchestration, но ни один service-specific account adapter полного цикла ещё не подключён.
2. Минимальные read-only adapters и fixture-based matching для Spotify, Apple, Yandex, Zvuk; каждый выводит нормализованные `TrackRef` плюс provider ID/ISRC/metadata/provenance.
3. Устранить author-credential dependency: проверить local Chrome extension/native helper flow для private APIs, Spotify direct login alternatives и Apple Music.app destination; не считать GitHub Pages достаточным для чужих origin/auth.
4. Пройти authenticated dry-run для всех четырёх source adapters и полный end-to-end transfer по одной паре с тестовым playlist/account; подтвердить read-back до включения массовых writes.
5. Только затем открыть все 12 pair selectors; незакрытая комбинация должна быть disabled с конкретной причиной, а не создавать ложное обещание.
