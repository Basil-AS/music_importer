# Матрица переноса между сервисами

Целевой сценарий — открыть штатные страницы музыкальных сервисов, войти в каждую свою учётную запись обычным способом, одним действием собрать доступные лайки и плейлисты и перенести их в выбранный сервис. Приложение не просит пароль, не требует OAuth-приложения владельца проекта и не загружает библиотеку на backend. Интерфейс включён в локальный Chrome extension и открывается значком; localhost-страница остаётся запасным путём.

«Реализованы» означает, что есть отдельные source readers, catalog search и target writers с fixture coverage. В 12 route fixtures теперь проходят нормализация целевого account snapshot для каждого провайдера, подбор записей без ISRC, построение transfer plan и запись лайков/плейлистов через общий движок в fake destination adapter. Отдельные provider fixtures проверяют source readers и реальные формы search/write commands. Fixtures моделируют ответы страниц/API и Chrome storage/tabs; это не live contract tests с пользовательскими сессиями. Ни одна из 12 направленных пар пока не имеет live end-to-end evidence. В текущем подключённом браузере доступна только localhost-страница; extension handshake и чтение живых аккаунтов не подтверждены.

## Автоматический подбор для больших библиотек

- Сопоставитель использует ISRC, название, исполнителя, альбом, длительность и признаки версии записи. Поисковый запрос включает доступный альбом и автоматически расширяется, только если точный запрос ничего не нашёл. Точные ISRC совпадения выбираются автоматически; metadata-only выбор требует высокого score и отрыва от второго кандидата. Повторные вхождения одной записи с устойчивым ID источника получают общий результат поиска для любого маршрута; ручной запрос не объединяется с автоматическим.
- Общий движок объединяет повторяющиеся запросы, ограничивает параллельность, повторяет временные ошибки и сохраняет прогресс. При HTTP 429 он передаёт заголовок `Retry-After` от каждого сервиса через extension bridge и ждёт заданное число секунд или HTTP-date; если заголовка нет, использует экспоненциальный backoff. Apple объединяет до 25 ISRC в один запрос; Spotify и остальные каталоги пока ищутся по одному треку.
- Для Spotify/Яндекса/Звука оценка для 1 000 разных треков — примерно 1 000–5 000 логических catalog-search запросов до повторов сетевых ошибок: базовый поиск, возможный ISRC lookup и до трёх широких вариантов запроса, если предыдущие кандидаты не проходят безопасный порог автоподбора. Кириллический вариант включается только для Яндекс Музыки и Звука, когда его обратная транслитерация совпадает с исходной строкой. Кэш и одинаковые записи уменьшают число запросов; retries могут его увеличить. Это расчёт по текущему алгоритму, не замер скорости и не утверждение о rate limit. У Spotify публичный `/search` ограничивает результат 10 объектами на тип; отдельный `GET /tracks?ids=...` batch endpoint был удалён в феврале 2026, но он выдавал metadata по уже известным ID и не заменял поиск ISRC. См. [Search API](https://developer.spotify.com/documentation/web-api/reference/search) и [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide).
- Экран отображает не более 50 строк за раз. Это снижает UI-нагрузку, но не сокращает число отдельных API-поисков для Spotify, Яндекс Музыки и Звука.
- Пороги не откалиброваны на размеченных пользовательских библиотечных данных. Предыдущий ручной прогон демо-выборки дал 4/6 автосовпадений до добавления правила для каталоговых дублей с одним ISRC; новое правило прошло fixture-проверку, но live демо повторно не прогонялось. Эта малая выборка не позволяет делать вывод о библиотеке или precision. Нельзя обещать, что для тысяч треков ручная проверка сведётся только к редким исключениям. До этого измеряются точность автоматических совпадений, ошибки по версиям и фактический rate limit каждого сервиса.

## Остаток до пригодного к повседневному использованию продукта

1. Загрузить/обновить unpacked extension в Chrome и открыть его значком. Live handshake и чтение пользовательских сессий ещё нужно подтвердить; localhost-разрешение для основного сценария не требуется. Если у открытой вкладки сервиса отсутствует content script, extension автоматически перезагрузит её один раз при запуске сканирования.
2. Снять read-only snapshots всех доступных аккаунтов и независимо подтвердить полноту каждой коллекции.
3. Прогнать все 12 route combinations на реальных тестовых библиотеках; сначала поиск и preview plan, затем маленькая запись с read-back.
4. Собрать labeled match decisions на разных языках, версиях, фичерингах и одинаковых названиях; настроить пороги на измеренную точность.
5. Измерить throughput и rate limits для нескольких тысяч tracks на каждом target. Добавлять batch API только там, где конкретный сервис действительно поддерживает групповой поиск.
6. Упростить распространение: сейчас требуется загрузить unpacked extension из исходников; установка через Chrome Web Store ещё не настроена. GitHub Pages deployment подготовлен, но требует включения в repo settings и release merge в `master`.
7. Проверить на живых аккаунтах восстановление после прерывания и закрытия вкладки. Recovery plan и target IDs хранятся локально; fixture-тесты всех четырёх writers подтверждают prefix-check, дозапись остатка и ожидание подтверждённой записи checkpoint перед добавлением треков. При потере ID или несовпадении порядка writers останавливаются для ручной сверки. Перед повседневным использованием нужно проверить на живых аккаунтах окна сбоя после создания playlist на сервере.
