# Матрица переноса между сервисами

Целевой сценарий — обычный вход в свои аккаунты, автоматический сбор доступных лайков и плейлистов и перенос в выбранный сервис. Extension сам открывает недостающие страницы сервисов в фоне и переключается на них только при явном действии «Войти». Вкладки остаются технически необходимы текущим адаптерам из-за сессий страниц и приватных API, но пользователю не нужно открывать их вручную. Приложение не просит пароль, не требует OAuth-приложения владельца проекта и не загружает библиотеку на backend. Интерфейс включён в локальный Chrome extension и открывается значком; localhost-страница остаётся запасным путём.

«Реализованы» означает, что есть отдельные source readers, catalog search и target writers с fixture coverage. В 12 route fixtures проходят нормализация целевого account snapshot для каждого провайдера, подбор записей без ISRC, построение transfer plan и запись лайков/плейлистов через общий движок в fake destination adapter. Отдельные provider fixtures проверяют source readers и реальные формы search/write commands. Fixtures моделируют ответы страниц/API и Chrome storage/tabs; это не live contract tests с пользовательскими сессиями. Ни одна из 12 направленных пар пока не имеет live end-to-end evidence. Последний документированный live read-only refresh 2026-10-31 показал ранее сохранённый полный снимок Apple Music, таймаут Spotify без нового полного снимка, подтверждённые лайки Яндекс Музыки при отказе проверки каталога плейлистов и лайки Звука при остановке на следующей странице каталога. Это не подтверждает каталоговый поиск, запись или полную пару source→target. Подробности и ограничения — в [журнале live-проверок](LIVE_VALIDATION.md).

## Автоматический подбор для больших библиотек

- Сопоставитель использует ISRC, название, исполнителя, альбом, длительность и признаки версии записи. Поисковый запрос включает доступный альбом и автоматически расширяется, только если точный запрос ничего не нашёл. ISRC совпадение выбирается автоматически, если title/album не указывают на конфликт версии; metadata-only выбор требует высокого score и отрыва от второго кандидата. Повторные вхождения одной записи с устойчивым ID источника получают общий результат поиска для любого маршрута; ручной запрос не объединяется с автоматическим.
- Общий движок объединяет повторяющиеся запросы, ограничивает параллельность, повторяет временные ошибки и сохраняет прогресс. При HTTP 429 он передаёт заголовок `Retry-After` от каждого сервиса через extension bridge и ждёт заданное число секунд или HTTP-date; если заголовка нет, использует экспоненциальный backoff. Для Spotify каталогный поиск и чтение страниц альбома теперь также проходят через общий сериализованный лимитер с интервалом 300 мс; live rate limits ещё надо измерить. Apple объединяет до 25 ISRC в один запрос. Все четыре цели также используют экспериментальный album-level batch для групп треков с общим альбомом и исполнителем; если безопасная группа не разрешается, включается индивидуальный поиск. Скорость и доля запросов, реально сэкономленных на живых каталогах, пока не измерены.
- Ранее индивидуальная схема для 1 000 разных треков оценивалась в 1 000–5 000 логических каталоговых запросов у Spotify/Яндекса/Звука до сетевых повторов. Теперь для всех четырёх целей включён experimental album-level batch: удачная группа может сократить индивидуальные запросы до одной album search и нескольких tracklist reads, а неудачная дополнительно запускает прежний per-track fallback. Фактическое количество зависит от числа уникальных альбомов, результатов и доли safe auto-match; точная экономия и throughput пока не измерены. Кириллический fallback остаётся только у Яндекса и Звука и включается при совпавшей обратной транслитерации. У Spotify текущая Search API ограничивает выдачу 10 объектами на тип. Отмена `GET /tracks?ids=...` в февральском migration guide относится к Development Mode-приложениям; Extended Quota Mode не затронут, а endpoint остаётся в reference. В этом проекте batch track lookup не используется: приватный session connector ищет по ISRC/метаданным и через album tracklists. См. [Search API](https://developer.spotify.com/documentation/web-api/reference/search), [Get Several Tracks](https://developer.spotify.com/documentation/web-api/reference/get-several-tracks), [February 2026 migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide).
- Экран отображает не более 50 строк за раз, чтобы не строить тысячи строк DOM одновременно. Само разбиение на страницы не сокращает сетевые вызовы: число запросов определяется повторами, album-level batch, безопасностью кандидатов и fallback на поиск отдельных треков.
- Пороги не откалиброваны на размеченных пользовательских библиотечных данных. До текущего правила дублей предыдущий ручной прогон демо-выборки дал 4/6 автосовпадений; теперь fixtures также покрывают дубли без ISRC только при точных названии, основном артисте, альбоме и длительности, и проверяют конфликтующие ISRC/длительность. Это всё ещё малая выборка и не позволяет делать вывод о библиотеке или precision. Нельзя обещать, что для тысяч треков ручная проверка сведётся только к редким исключениям. До этого измеряются точность автоматических совпадений, ошибки по версиям и фактический rate limit каждого сервиса.

## Остаток до пригодного к повседневному использованию продукта

1. Загрузить/обновить unpacked extension в Chrome и открыть его значком. Live handshake и чтение пользовательских сессий ещё нужно подтвердить; localhost-разрешение для основного сценария не требуется. При первом сканировании extension создаёт недостающие service tabs в фоне; если у открытой вкладки отсутствует content script, он перезагрузит её один раз.
2. Снять read-only snapshots всех доступных аккаунтов и независимо подтвердить полноту каждой коллекции.
3. Прогнать все 12 route combinations на реальных тестовых библиотеках; сначала поиск и preview plan, затем маленькая запись с read-back.
4. Собрать labeled match decisions на разных языках, версиях, фичерингах и одинаковых названиях; настроить пороги на измеренную точность.
5. Измерить throughput и rate limits для нескольких тысяч tracks на каждом target. Добавлять batch API только там, где конкретный сервис действительно поддерживает групповой поиск.
6. Упростить распространение: сейчас требуется загрузить unpacked extension из исходников; установка через Chrome Web Store ещё не настроена. GitHub Pages deployment подготовлен, но требует включения в repo settings и release merge в `master`.
7. Проверить на живых аккаунтах восстановление после прерывания и закрытия вкладки. Recovery plan и target IDs хранятся локально; fixture-тесты всех четырёх writers подтверждают prefix-check, дозапись остатка и ожидание подтверждённой записи checkpoint перед добавлением треков. При потере ID или несовпадении порядка writers останавливаются для ручной сверки. Перед повседневным использованием нужно проверить на живых аккаунтах окна сбоя после создания playlist на сервере.

## Все направленные пары

На уровне API-шаблонов source-read и target-write операции существуют у всех четырёх сервисов, так что все 12 комбинаций имеют технические кандидаты для likes и playlists. Ни одна пара пока не является готовой функцией продукта: ни для одного target не выполнен полный тестовый transfer с обратным чтением, а вход/полнота отдельных источников остаются условными. Клетка показывает, какие adapter gaps надо закрыть для конкретного направления; это не обещание, что API допустим или стабилен.

| Источник → назначение | Spotify | Apple Music | Яндекс Музыка | Звук |
|---|---|---|---|---|
| **Spotify** | — | Spotify read/auth частично private; Apple writer fixture-tested; live page session/transfer unverified | Spotify read/auth частично private; Yandex writer fixture-tested, target session/live write unverified | Spotify read/auth частично private; Звук write schema/auth |
| **Apple Music** | Apple source read confirmed once live; Spotify write OAuth/client constraints and route unverified | — | Apple source read confirmed once live; Yandex writer/session and route unverified | Apple source read confirmed once live; Zvuk destination auth/write and route unverified |
| **Яндекс Музыка** | Яндекс source paging/auth incomplete; Spotify write OAuth/owner constraint | Яндекс source paging/auth incomplete; Apple writer fixture-tested; both live session/transfer unverified | — | Яндекс source paging/auth incomplete; Звук destination auth/write verification |
| **Звук** | Звук read count mismatch/auth; Spotify write OAuth/owner constraint | Звук read count mismatch/auth; Apple writer fixture-tested; both live session/transfer unverified | Звук read count mismatch/auth; Yandex writer fixture-tested, target session/live write unverified | — |

У каждого направления те же типовые задачи остаются отдельно для likes и playlist items. Для playlists требуется сохранить порядок, повторяющиеся записи и доступность; для favorites — не подменять нативную коллекцию обычным playlist без выбора пользователя. Треки, которых нет в каталоге назначения, должны остаться в отчёте пропусков, а не исчезнуть из количества.

## Сопоставление больших библиотек

Чтобы не сверять тысячи записей вручную, общий engine должен:

1. Сохранять исходный provider ID и использовать его для повторов и дубликатов; использовать ISRC там, где обе стороны его раскрывают.
2. Нормализовать Unicode, регистр, пунктуацию и метки версий (live/remaster/radio edit), затем ранжировать кандидатов по названию, артистам, альбому, длительности и региональной доступности.
3. Автоматически принимать только кандидаты выше откалиброванного high-confidence порога; показывать компактный review queue лишь для коллизий/низкой уверенности.
4. На каждой странице сохранять cursor/checkpoint. Для source totals сверять `total`, count и уникальные IDs; если API противоречит сам себе, не объявлять экспорт полным.
5. После batch writes прочитать назначение обратно, подтвердить фактические items и продолжать с последнего проверенного checkpoint после ошибки/429.

Никакой API ещё не демонстрирует сквозную end-to-end автоматизацию тысяч композиций в приложении Music Importer. Из текущих источников Spotify и Apple дают лучшие документированные каталожные идентификаторы; Yandex/Zvuk могут требовать metadata scoring, а Звук не возвращает `isrc` в проверенной Track GraphQL schema. Поэтому порог авто-переноса надо калибровать по test fixtures и не обещать 100% автоматического exact match.

1. Завершить единый provider adapter contract: `connect`, paged `discoverCollectionPage`, `readCollectionPage`, `searchTracks`, `readDestination`, `writeFavorites`, `createPlaylist`, `writePlaylistItems`, `readBack`, `disconnect`. PR #2 содержит общий cursor reader/search orchestration, четыре experimental source readers и fixture-tested Apple/Yandex target writers; live account coverage and Spotify/Zvuk targets remain incomplete.
2. Минимальные read-only adapters и fixture-based matching для Spotify, Apple, Yandex, Zvuk; каждый выводит нормализованные `TrackRef` плюс provider ID/ISRC/metadata/provenance.
3. Устранить author-credential dependency: проверить local Chrome extension/native helper flow для private APIs, Spotify direct login alternatives и Apple Music.app destination; не считать GitHub Pages достаточным для чужих origin/auth.
4. Пройти authenticated dry-run для всех четырёх source adapters и полный end-to-end transfer по одной паре с тестовым playlist/account; подтвердить read-back до включения массовых writes.
5. Только затем открыть все 12 pair selectors; незакрытая комбинация должна быть disabled с конкретной причиной, а не создавать ложное обещание.
